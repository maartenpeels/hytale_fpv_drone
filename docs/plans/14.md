# Plan — #14 Angular-rate PID controller

Ticket: [#14](https://github.com/maartenpeels/hytale_fpv_drone/issues/14) · Epic: #4 · Milestone: v0.1 — Feel

## What the ticket asks for

The controller that turns a *demanded angular rate* into the torque the integrator applies —
P, I and D per axis. Gains are values passed in, not constants, because #5 persists them per
pilot. Integral windup handled explicitly, with "a quad held against a wall at full stick" named
as the case that exposes it.

Done when tests cover convergence to a demanded rate, no steady-state error with an integral
term, overshoot at high P, and bounded windup when the demanded rate cannot be reached.

## What is already there

#13 landed the dynamics and left this seam open with a documented placeholder:

```java
/** Placeholder for #14's PID. */
private double torqueDemand(double actualRate, double demandedRate, double authority) {
    double error = demandedRate - actualRate;
    return Math.clamp(error / (parameters.rateTimeConstant() * authority), -1.0, 1.0);
}
```

Proportional only, one shared time constant, no memory. #13's own plan flagged the consequence:
a proportional tracker cannot hold a rate against sustained drag, so the model feels stiff until
this ticket lands. That is the steady-state error the integral term exists to kill, and it is
already measurable — which makes it the natural first test.

Two facts inherited from #13 that shape the design:

1. **Torque demand is normalised to `[-1, 1]` per axis** — that is `MotorMixer.mix`'s contract,
   and the mixer is what turns demand into commands and then into achieved thrust.
2. **Achieved torque does not equal demanded torque**, because mixing is linear in command space
   while thrust goes with the square of the command. #13 called this "exactly the error a real
   rate PID exists to close". So the loop this controller closes is genuinely non-linear and
   throttle-dependent; it is not a textbook first-order plant.

## Design

### Output space: normalised torque, not angular acceleration

The controller outputs a normalised torque demand in `[-1, 1]`, the mixer's units — not rad/s².

The alternative (output rad/s², let the integrator divide by `authority` and clamp) makes gains
airframe-independent, which is superficially attractive. It is wrong here: **saturation is the
whole subject of this ticket**. If the integrator does the clamping, the controller cannot see
that its output was clipped, and conditional anti-windup becomes impossible without plumbing the
saturation flag back. Owning the clamp means owning the windup fix, in one class, with one test.

Consequence: gains carry the airframe's authority inside them. `proportional` is in units of
normalised-torque per rad/s of rate error. That is also how a real flight controller's gains
work, so it is the familiar shape for anyone who has tuned Betaflight.

### Derivative on measurement, not on error

`d(error)/dt = d(setpoint)/dt − d(measurement)/dt`. Using the full error derivative means a stick
snap — an instantaneous setpoint step — produces a derivative spike of `kd · Δsetpoint / dt`,
which at 4 ms and a 800 °/s stick throw is enormous and purely an artefact. Betaflight derives on
gyro for exactly this reason.

So the D term is `−kd · (rate − lastRate) / dt`, and `lastRate` is part of the controller state.
This has one edge: a controller state created with `lastRate = 0` while the drone is already
rotating produces a one-step phantom spike. Handled by a `RatePidState.at(BodyRates)` factory for
spawning mid-motion, with `ZERO` defined as `at(BodyRates.ZERO)` — no `primed` boolean, no
branch.

### Anti-windup: clamp the accumulated term, and freeze it while saturated

Both, because they fix different failures.

- **Clamp.** The integral is accumulated *already scaled by* `ki` and capped at
  `±integralLimit`. Accumulating the scaled term rather than raw `∫e·dt` means `integralLimit` is
  expressed directly as a fraction of output authority, which is the thing the ticket cares about
  bounding; and it means a live gain change (#5) does not retroactively rescale history into a
  jolt.
- **Freeze.** Even a clamped integral is wrong to keep growing while the output is already
  saturated and the error is pushing it further out. So: if the unsaturated sum is outside
  `[-1, 1]` and the error has the same sign as that sum, the integral is held. Error reversing
  sign always unfreezes it, so recovery is immediate rather than waiting for the accumulator to
  bleed down.

The wall case — held against a wall at full stick — is exactly this: rate pinned at zero,
maximum error forever, output saturated. Clamp alone bounds the accumulator; freeze alone bounds
it too but only if the clamp is loose; together the released drone gets at most `integralLimit`
of stale correction, for one step.

### Where the controller's state lives

The controller has memory (integral, last rate), so something has to carry it between steps. The
integrator's current signature has nowhere to put it, and **`DroneState`'s javadoc explicitly
rules itself out**:

> Nothing else is carried — no accumulated PID error, no timestamps, no identity — so a step is a
> pure function of `(state, input, dt)`.

That was a deliberate choice in #13 and this plan keeps it. Instead:

```java
record FlightState(DroneState drone, RatePidState controller)

FlightState step(FlightState state, ControlInput input, double dt)
```

`DroneState` stays purely kinematic, the step stays a pure function of `(state, input, dt)`, and
downstream code that only wants geometry (#21 collision, #20 body-follow) reads
`state.drone().position()`.

**Cost, stated plainly:** `QuadIntegrator.step` changes shape, so #13's `QuadIntegratorTest`
(469 lines) is edited throughout. The change is mechanical — `DroneState` → `FlightState` at the
loop variable, `.drone()` inserted at the assertions — but it is a real diff over code merged an
hour ago. The alternative, putting the accumulator in `DroneState`, is a smaller diff today and
contradicts that type's stated contract; #21 and #23 would then inherit a `DroneState` that is
part physics and part controller. Not worth it.

### Gains do not go in `QuadParameters`

`QuadParameters` is the *airframe*; gains are the *pilot's tune*, and #5 persists them per player
while the airframe stays server-wide. So `RatePidGains` is its own value, and the integrator
takes both:

```java
QuadIntegrator(QuadParameters parameters, RatePidGains gains)
QuadIntegrator(QuadParameters parameters)   // RatePidGains.DEFAULT
```

Both immutable, so a retune in #5 is a new integrator rather than mutable state — one small
allocation per pilot per retune. No `withGains` yet; adding it before #5 has a call site would be
speculative.

`QuadParameters.rateTimeConstant` becomes dead once the placeholder is gone and is **removed**.
It existed only to parameterise the placeholder. `rollPitchAuthority` and `yawAuthority` stay —
they are physical (rad/s² at full differential thrust) and the integrator still uses them to turn
achieved thrust differentials into angular acceleration.

### Default gains

Derived, not invented, so the change is neutral on feel until someone deliberately tunes it:

- `proportional` reproduces #13's placeholder exactly — `1 / (rateTimeConstant · authority)` at
  the old defaults, which is `≈0.191` per rad/s for roll and pitch and `≈0.764` for yaw. Yaw is
  four times higher because yaw authority is four times weaker; per-axis gains are the reason
  that falls out instead of needing a special case.
- `integral` and `derivative` start from integral and derivative times of ~0.15 s and ~0.01 s
  against that P, then get adjusted against the step-response tests until rise time and overshoot
  are what a racing quad feels like. **They landed at 0.3 s and 0 s** — see "Measured results".
- `integralLimit` defaults to `0.3` — a third of output authority, in Betaflight's ballpark.

Like #13's drag coefficients, these are judgements about *feel* that #24 settles; they are
parameters precisely so settling them is a config change.

## Files

All under `fpv-core/src/**` and `docs/plans/**` — both "always" paths in CLAUDE.md. Nothing in
`:fpv-plugin`, no build changes, no dependencies.

New, in `fpv-core/src/main/java/com/maartenpeels/fpv/flight/`:

```
PidGains.java        one axis: proportional, integral, derivative, integralLimit; validated
RatePidGains.java    roll/pitch/yaw PidGains + DEFAULT
PidState.java        one axis: accumulated integral term, last measured rate
RatePidState.java    roll/pitch/yaw PidState + ZERO + at(BodyRates)
TorqueDemand.java    normalised roll/pitch/yaw torque, [-1, 1], mixer's units and signs
RatePid.java         the controller; immutable, holds gains
RatePidUpdate.java   (TorqueDemand torque, RatePidState state) — update's two return values
FlightState.java     (DroneState drone, RatePidState controller)
```

The per-axis / triple pairing is deliberate: a flat `RatePidGains` of twelve doubles is the
transposition bug `QuadParameters` already warned about, and per-axis is the unit a pilot tunes
in.

Modified:

```
QuadIntegrator.java   placeholder torqueDemand() deleted, RatePid wired in, step() takes FlightState
QuadParameters.java    rateTimeConstant removed
```

Tests mirrored one `*Test` per new class, plus edits to `QuadIntegratorTest` and
`QuadParametersTest`.

## Test strategy

`ControlInputTest` conventions — `@Nested` per behaviour group, names that state the *reason*.

The four the ticket names:

- `convergesOnTheDemandedRateFromRest` — constant demand, plant driven by the real integrator;
  rate reaches the demand and stays.
- `holdsTheDemandedRateWithNoSteadyStateErrorBecauseTheIntegralAbsorbsDrag` — the same run with
  `integral` zeroed leaves a measurable offset (that is #13's stiffness, asserted rather than
  described); with the integral term the residual goes to near zero.
- `overshootsBeforeSettlingWhenProportionalGainIsHigh` — a high-P profile overshoots the demand
  and then settles; the default profile does not overshoot past a stated bound. Asserts the
  *shape* of the response, not one sample.
- `boundsTheIntegralWhenTheDemandedRateCannotBeReached` — the wall: rate forced to zero, full
  demand held for seconds. The accumulated term stops at `integralLimit`; the output stays inside
  `[-1, 1]`; and on release the drone does not receive more than `integralLimit` of stale
  correction.

Plus the things flying cannot check:

- **D on measurement**: a step change in demand produces no derivative spike — contrasted against
  the same step with a moving measurement, which does produce D action. This is the test that
  would fail if someone "simplified" it to D-on-error.
- **Freeze vs clamp are both load-bearing**: with a generous `integralLimit`, the accumulator
  still stops growing while saturated; with freeze disabled by a sign-reversing error, it moves
  immediately.
- `RatePidState.at()` — spawning a controller for a drone already rotating produces no
  first-step derivative kick, where `ZERO` would.
- Output is always within `[-1, 1]`, for absurd gains and absurd errors.
- Determinism: identical arguments twice, bit-identical output.
- Validation: negative or non-finite gains rejected; zero gains accepted, because P-only and
  PI-only are legitimate profiles a pilot might tune to.
- `TorqueDemand` range validation and sign convention documented against the mixer's.

Regression coverage of the code this change touches:

- `QuadIntegratorTest`'s hover, ballistic-fall, terminal-velocity and dt-invariance tests are
  kept and must still pass — they are the guard on decision 3's escape hatch, and re-running them
  through the PID is how we learn whether the closed loop is dt-stable.
- One new integrator-level test: a sustained roll demand now *reaches* the demanded rate, which
  the P-only placeholder provably could not.
- `QuadParametersTest` loses its `rateTimeConstant` cases.

The area is fully tested already (#13 shipped 8 test classes over it), so `/write-tests` is not
needed first.

## Risks and open questions

1. ~~**Closed-loop stability at coarse `dt`.**~~ **Confirmed, and it is the plant's fault, not the
   gains'.** At `substeps = 1` (33 ms) the drone mistracks its rate demand by +37 %, and a
   proportional-only loop mistracks by the same amount — no tuning rescues it. The default 8
   substeps has a 4× margin. The follow-up is a minimum substep count in `FpvConfig`, which is
   `:fpv-plugin` and belongs to #23. See "Measured results" for the numbers and the test that pins
   them.
2. **`QuadIntegrator.step`'s signature changes**, and #13's tests churn with it. Reasoning above;
   calling it out because the code being edited was merged today and nothing outside `:fpv-core`
   depends on it yet, which is precisely why now is the cheap moment.
3. **`QuadParameters` loses a record component.** Public shape change in `:fpv-core`, no
   consumers outside the module, builder unaffected for every other field.
4. **Default gains are informed guesses about feel.** Same standing as #13's drag and
   thrust-to-weight numbers; #24 judges them. The P defaults are chosen to reproduce #13's
   behaviour exactly, so nothing regresses on feel — the model only gains the ability to hold a
   rate.
5. **The plant is non-linear**, throttle-dependent and saturating (achieved ≠ demanded torque, by
   #13's design). So classic tuning rules do not transfer, and the tests assert response
   *properties* — converges, no steady-state offset, bounded overshoot, bounded windup — rather
   than numeric trajectories that would be brittle.
6. **No derivative low-pass filter, and no derivative action by default.** Real flight controllers
   filter D heavily because gyro noise is real; there is no noise in a deterministic simulation, so
   a filter would add a tunable nothing here can justify. The measurements then went further: this
   plant has no lag for D to anticipate either, so the default derivative time is **0**. The term
   is implemented and tested because #5 exposes it to pilots and because any future motor-response
   model makes it useful — but shipping a rate loop that is a PI in its default tune is a deliberate,
   measured choice, not an oversight.

## Measured results

Taken off the finished controller on the default airframe, so the tolerances in the tests are
justified rather than guessed. Roll axis, half stick (400 °/s demanded), 30 TPS × 8 substeps
unless stated.

### Final default tune

| Gain | Roll / pitch | Yaw | Where it comes from |
| --- | --- | --- | --- |
| `proportional` | 0.19099 | 0.76394 | `1 / (0.03 s · authority)` — #13's placeholder, as a gain |
| `integral` | 0.63662 | 2.54648 | integral time 0.3 s |
| `derivative` | 0 | 0 | see below |
| `integralLimit` | 0.3 | 0.3 | a third of output authority |

### Step response

| Measurement | Result |
| --- | --- |
| Steady-state error, quarter / half / full stick | **+0.14 % / +0.11 % / +0.03 %** of demand |
| Steady-state error with the integral term removed | **−1.478 %**, at every stick position |
| Overshoot, half stick | **+2.32 %** |
| Rise time to 90 % of demand, half stick | **41.7 ms** |
| Yaw, half stick | +0.03 % error, +0.55 % overshoot |

The −1.478 % figure is #13's stiffness made a number: a proportional-only loop settles where its
output balances drag and the mixer's losses, which is always short of the demand. Killing it was
the point of the ticket.

### Windup

| Case | Result |
| --- | --- |
| Held against a wall, full stick, 10 s | accumulator stays at **exactly 0**, output pinned at 1.0 |
| Unreachable 2 rad/s demand, output unsaturated, 10 s | accumulator stops at **exactly 0.3** — the clamp |
| Error reverses after 10 s wound up | accumulator moves on the **next step** |

The wall case never touches the clamp, because full stick saturates the output on the
proportional term alone and the freeze engages on step one. The 2 rad/s case never touches the
freeze, because the output stays at 0.68. Neither guard would have been enough alone, which is
why both are there and why both have their own test.

### Derivative on measurement

At a derivative time of 0.008 s and a 4.2 ms step, `kd/dt` is **0.367** — a third of full
authority that a derivative-on-error implementation would inject on every stick snap, purely as
an artefact. Measured: a pure setpoint step produces **identical** torque at every derivative
time tried (+0.19364), while a measurement change of the same size moves it from −0.194 to
−0.560. The setpoint genuinely never enters the derivative.

Priming matters more than expected: a controller given `RatePidState.ZERO` for a drone already
rolling at 6 rad/s answers a *zero* error with **−1.0**, full opposing torque, for one step.
`RatePidState.at()` answers 0.0.

### Why the derivative default is zero

| Integral time | Derivative time | Overshoot | Rate past centre on stick release | Kick recovery |
| --- | --- | --- | --- | --- |
| 0.15 s | 0 | +5.33 % | −0.347 | 33 ms |
| 0.15 s | 0.008 s | +9.27 % | −0.628 | 46 ms |
| **0.3 s** | **0** | **+2.32 %** | **−0.143** | **38 ms** |
| 0.3 s | 0.008 s | +4.80 % | −0.314 | 54 ms |
| 0.5 s | 0 | +0.95 % | −0.049 | 42 ms |

Derivative action made every metric worse at every integral time tried. That is not a tuning
failure, it is the plant: torque becomes angular acceleration inside one step, and the airframe's
own `angularDrag` is already a rate-proportional damping term, so the rate loop is first order and
a PI controller closes it about as well as it can be closed. Derivative action earns its place
against lag — motor spin-up, prop inertia, frame flex, gyro filtering — and #13's model has none.

The term is implemented and tested regardless: it is a gain #5 hands to pilots, and it stops being
useless the moment the model grows any lag of its own.

### Substep count — the one real finding

| Substeps per 30 TPS tick | `dt` | Steady-state error |
| --- | --- | --- |
| 1 | 33.3 ms | **+37.5 %** |
| 2 | 16.7 ms | +0.10 % |
| 4 | 8.3 ms | +0.08 % |
| 8 (`FpvConfig` default) | 4.2 ms | +0.11 % |
| 16 | 2.1 ms | +0.13 % |
| 64 | 0.5 ms | +0.12 % |

**At one substep per tick the drone mistracks its rate demand by 37 %.** Risk 1 above anticipated
this and guessed the gains would be at fault; they are not. A proportional-only loop mistracks by
the same +37 % at that step size, and no combination of integral and derivative time rescues it —
it is the plant being sampled too coarsely, and the rate loop merely inherits it.

Two consequences:

- `FpvConfig`'s default of 8 substeps has a **4× margin** over the point where tracking degrades.
  Nothing needs to change for the default configuration.
- `physicsSubsteps = 1` is not a usable setting, and `FpvConfig` does not currently say so. That
  is a `:fpv-plugin` change and belongs to #23, which owns the substep loop — flagged there rather
  than done here. `RatePidTest.tracksAtEverySubstepCountFromTwoUpwards` pins both halves so the
  finding cannot quietly rot.

Also confirmed: the loop stops settling at all past roughly eight times the default proportional
gain (68 % overshoot, then sustained oscillation), which is what makes the high-P overshoot test
meaningful rather than arbitrary. In the *saturated* regime — full stick — raising P changes almost
nothing, because the mixer's ceiling dominates. True of a real quad too.
