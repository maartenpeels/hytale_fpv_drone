# Plan — #26 Replace the unmodified Hytale Plugin Template README

Ticket: [#26](https://github.com/maartenpeels/hytale_fpv_drone/issues/26) · Epic: #4 · Milestone: v0.1 — Feel

## What the ticket asks for

`README.md` is still upstream's template readme. It documents how to *use the template* —
"Copy the template", "Update the project values in `gradle.properties`", "Add your own license
after copying" — none of which is true of this repo any more. Replace it with a readme for
someone arriving at this project cold.

Must cover: what the plugin does, the JDK 25 requirement, how to build and run, the two-module
split. Plus the two traps the ticket calls out by name:

- Gradle itself needs JVM 25, not just the compile step.
- The plugin jar builds to `fpv-plugin/build/libs/`, not `build/libs/`.

## The division of labour with CLAUDE.md

This is the constraint that shapes the whole document. `CLAUDE.md` is 489 lines of durable agent
context: verified facts about the decompiled server, settled decisions with their rationale,
boundaries. The README is the front door for a human — orientation, then the shortest path to a
running build.

So the README:

- **States** what the project is, where it is on the roadmap, how to build, run and test it, what
  lives in which module, and how to contribute.
- **Links** to `CLAUDE.md` for the reasoning — the decompiled-source workflow rule, the physics
  decisions, the boundaries — rather than restating it. Nobody wants two copies of "gravity is
  32.0, not 9.81" drifting apart.
- **Stays well under** CLAUDE.md's length. If a section is only interesting to someone changing
  the code, it belongs in CLAUDE.md.

Anything a reader needs *before* they decide to build gets stated; anything they need *while*
changing the physics gets linked.

## Honesty about status

The repo is mid-phase-0 and the README should say so plainly. As of this change:

- `:fpv-core` has the flight model — `QuadIntegrator`, `RatePid`, `RateCurve`/`RateProfile`,
  `MotorMixer`, `Quat`/`Vec3` — with a test per class (#13, #14, #15 merged).
- `:fpv-plugin` has the entry point, `FpvConfig` and a `/fpv` command that prints the resolved
  tick/substep settings. **There is no flyable drone yet.** #16–#24 are the rest of phase 0.

A readme that implies you can `/fpv launch` today would be a lie, and the first thing a visitor
would discover. State the milestone question — *does a server-simulated drone at 30 TPS feel
flyable at all?* — as still open.

## Commands: only ones that have been run

CLAUDE.md's hard rule. For this change that means:

| Command | Treatment |
| --- | --- |
| `./gradlew build` | Run in this worktree before the PR; documented as verified |
| `./gradlew :fpv-core:test` | Same |
| `./gradlew setupHytaleDev` | Documented as the dev flow, **not** claimed as run — it mutates the local Hytale dev environment |
| `./gradlew runServer` | Same — it blocks on a running server |
| `./gradlew hytaleJvmDoctor`, `updatePluginManifest`, `--refresh-dependencies` | Listed from CLAUDE.md's Commands section, which already carries them |

The two unverified ones are the actual dev loop, so omitting them would make the README useless.
They are presented as the documented flow without a claim that this change exercised them.

## Files to touch

- `README.md` — full rewrite.
- `docs/plans/26.md` — this document.

Nothing else. Specifically **not**:

- `CLAUDE.md` — its "Known repo issues" section lists the template README, and the ticket asks for

  conflict. Flagged in the PR body instead.
- `LICENSE` — #25 is adding it in parallel. The README references MIT (per `mod_license` in
  `gradle.properties`) and points at the file; it does not create it.
- `gradle.properties`, `*.gradle.kts` — ask-first paths, and nothing here needs them.

## Test strategy

There is no test for prose. What is verifiable is that the commands work and the claims match the
tree, so:

1. `./gradlew build` and `./gradlew :fpv-core:test` in this worktree, with the JDK 25 prefix — both
   must pass, and the build must produce the jar at the path the README claims.
2. `ls fpv-plugin/build/libs/` to confirm the jar name and location, including the space in
   `FPV Drone-0.0.1.jar` that #27 tracks.
3. Every module, class and file path named in the README checked against the actual tree.
4. Every link resolved — relative paths to repo files, absolute URLs for external ones.

## Risks

- **Duplication drift.** Mitigated by linking rather than restating; the only facts duplicated are
  the two the ticket explicitly asks for (JDK 25, jar path), which are build-entry facts a human
  needs before they read anything else.
- **Status going stale.** The status section is written against issue numbers and the milestone
  question, so it stays legible even once it's out of date, and the next phase-0 PR can move it.
