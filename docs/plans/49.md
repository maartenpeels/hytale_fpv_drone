# 49 — Instrument the inbound input path

## Why this became necessary rather than nice

Four flight sessions produced symptoms rather than diagnoses. #47 ("no pilot input reaches the
drone") had four hypotheses and no way to test any of them from outside the process, because
`/fpv camera status` counts *outbound* packet 280s and nothing at all reported the inbound side.

Two of the four were closed without this ticket, and both are worth recording because they show
what was left:

- **The camera lock.** Flown with `/fpv camera set --locked false`, confirmed live by `re-attached`
  and `locked=false flying=true droneNetworkId=289`, with `SetServerCamera … sent to you: 2` proving
  the client received the attach. **Input stayed completely dead.** Eliminated by experiment.
- **A UUID key mismatch**, the prime suspect, and the one that was invisible by construction.
  Eliminated by reading: `Universe.addPlayer` builds both from the same expression —

  ```java
  PlayerRef playerRefComponent = new PlayerRef(holder, auth.getUuid(), ...);
  holder.putComponent(UUIDComponent.getComponentType(), new UUIDComponent(auth.getUuid()));
  ```

  (`server/core/universe/Universe.java:1013-1019`). Same value, same holder, and the `putComponent`
  overwrites any stale persisted component, so no divergence path exists.

Also ruled out by reading, so nobody re-treads it: the watcher *is* registered
(`FPVDrone.java:112`); `PacketAdapters.__handleInbound` fires for **every** inbound packet before
dispatch, unconditionally (`server/core/io/netty/PlayerChannelHandler.java:30`); the vanilla client
genuinely populates `wishMovement`, since the server itself consumes it
(`GamePacketHandler.java:315`); and all three flight systems are registered, with the original 1 g
climb proving `AdvanceFlight` ticks.

What remains cannot be seen from outside, and #45 is the reason. Fixing the hover throttle made
**every** failure mode terminate at `PilotInputMapper.hovering()`:

| Cause | Behaviour |
| --- | --- |
| No slot for the pilot's key | `AdvanceFlight`'s missing-slot fallback → `hovering()` |
| Slot open, no packets arriving | staleness cutoff → `centred()` → `hovering()` |
| Slot open, packets arriving empty | mapper maps all-zero wish → `hovering()` |

All three are a drone sitting perfectly still. That is a better diagnostic baseline than a runaway
climb, and it is also three distinct bugs wearing one face.

## What was built

Counters at each stage, and one command that reads them and **names the failure mode**.

- `ClientMovementWatcher` — `inboundPackets` (any type), `movementPackets`, `watcherErrors`.
  `accept` now wraps its body in `try/catch Throwable`, counts, and **rethrows** so
  `PacketAdapters` still logs the cause at SEVERE. Before this, a watcher throwing on every packet
  and a watcher never invoked produced identical evidence: all counters zero.
- `PilotInputBuffer` — `offersAccepted`, `offersDropped`, `openKeys()`. The drop is correct
  behaviour (a `computeIfAbsent` would grow an entry per player who ever moved) that is
  indistinguishable from a bug, which is precisely the shape of the eliminated hypothesis.
- `PilotInputSlot` — `lastInput()` (null until first tick), `heldSeconds()`, `offers()`, `held()`.
- `/fpv input status` — the whole chain plus a verdict.

### Two design points worth defending

**The verdict line is the deliverable, not decoration.** Eight numbers still need interpreting
mid-flight, which is exactly when a pilot is least able to do it. `verdict(...)` walks the stages
*in the order the path runs* and reports the first broken one. Computing it backwards from the
sticks would blame the mapper for a missing slot, since both end in centred sticks.

**`PilotInputBuffer` lost its `final`.** Nothing inside the watcher's try block can be made to throw
from the outside — by design, every sanitising rule lives in the core mapper, which never throws —
so a test subclass overriding `offer` is the only way to exercise the error counter. An instrument
whose own failure path is unverifiable is what #47 already had.

## Testability

`accept(PlayerRef, Packet)` delegates to a package-private `accept(UUID, Packet)`. The harness
cannot construct a `PlayerRef` — the same constraint that made #19 introduce its `PilotSink` seam —
so the seam puts everything with behaviour on the testable side, leaving only "which UUID a
connection reports", which is now pinned by reading instead.

`:fpv-plugin` 176 → 196 tests. `:fpv-core` unchanged at 426; nothing in core was touched.

## Explicitly not in scope

Fixing #47. This makes it diagnosable and does not decide which hypothesis is right.

## How to read the output

Run `/fpv camera on`, then `/fpv input status`. The verdict names the stage; the lines above it show
the working. The two readings that matter most:

- **`watcher: inbound(any)=0`** — the watcher is not in the pipeline. Suspect a hot reload leaving a
  stale registration, not the input mapping.
- **`movement=0` with a non-zero `received` count** — the connection got packet 108 and the watcher
  never saw it, which would be a fault between the netty pipeline and us.

If instead the path is healthy and the sticks are non-centred, the input path is exonerated and #47
is downstream — which would be a genuinely new result, since every hypothesis so far has been
upstream.
