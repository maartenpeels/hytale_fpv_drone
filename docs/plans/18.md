# #18 — Drone entity: pack model, spawn and despawn lifecycle

Branch `feat/18-drone-entity`, off `main`. Originally cut from `feat/34-plugin-test-harness`
(PR #37) for the `:fpv-plugin` ECS harness this work is tested with; #37 has since merged, so
the branch now targets `main` directly.

Part of #4 (phase 0). Four tickets sit on top of this one — #19 camera attach, #20 body-follow,
#22 `/fpv launch` / `/fpv land`, #23 flight tick — and all four build on the per-pilot
flight-session ownership model established here. That model, not the mesh, is the deliverable.

---

## The question this ticket actually answers

Not "how do I spawn an entity" — that turned out to be five lines. The question is:

> **Where does flight-session state live, such that no exit path can leak a drone?**

The exit paths are: `/fpv land`, hard disconnect mid-flight, kick, world switch mid-flight,
world unload, world crash, clean server shutdown, and `kill -9`. Eight paths. Any design that
needs eight pieces of cleanup code is wrong.

### The answer: the session is a component on the pilot; the drone entity is non-serialized

Two facts, both read out of the decompiled server, collapse eight paths into two hooks and one
flag:

1. **Every player exit is one ECS operation.** `PlayerRef.removeFromStore()`
   (`server/core/universe/PlayerRef.java:161`) is
   `entity.getStore().removeEntity(entity, RemoveReason.UNLOAD)`, and it is reached by
   disconnect, kick, world switch and world crash alike — via `Universe.removePlayer`
   (`Universe.java:1136-1148`) and `World.stopIndividualWorld` (`World.java:286-291`).
   So a `RefSystem` whose query is *our session component* gets exactly one
   `onEntityRemove(ref, reason, store, commandBuffer)` call per exit, with the pilot ref still
   valid and a `CommandBuffer` in hand (`component/Store.java:655-664`).
   Note: the reason is **always `UNLOAD`**, never `REMOVE`, so we must not branch on it.

2. **Non-serialized entities cannot outlive the process.**
   `ComponentRegistry.getNonSerializedComponentType()` (`component/ComponentRegistry.java:246`)
   is what projectiles and dropped items use (`ProjectileModule.java:143`,
   `DeployablesUtils.java:83`). A drone carrying it is never written to a chunk or world save,
   so `kill -9` mid-flight leaves nothing behind *by construction*. That is a stronger
   guarantee than any shutdown hook, and it needs to be, because the hooks are unreliable:
   `PluginManager.shutdown()` only calls a plugin's `shutdown()` when its state is `ENABLED`
   (`PluginManager.java:398`), and `Universe.shutdownAllWorlds()` never even fires
   `RemoveWorldEvent` (`Universe.java:678-686`).

So: **session state on the pilot entity, drone entity non-serialized, and the ECS removal
callback is the single teardown choke point.** No `Map<UUID, ...>`, and no shutdown hook.

### Why not a plugin-side map

The codebase settles this argument against itself. `ParkourPlugin` keeps
`Object2IntMap<UUID> currentCheckpointByPlayerMap` (`builtin/parkour/ParkourPlugin.java:27-28`),
removes from it only on course completion (`ParkourCheckpointSystems.java:186`), has no
`PlayerDisconnectEvent` listener, and its `HolderSystem.onEntityRemoved` is empty
(`ParkourCheckpointSystems.java:47-48`) — **a player who disconnects mid-course leaks two map
entries permanently.** `BuilderToolsPlugin` keeps a similar map and pays for it with a
`ScheduledFuture` sweeper, a retain/release pair of event listeners and a retention timestamp
(`BuilderToolsPlugin.java:324-333, 761-773, 857-883`). The same plugin's *component*-based
per-player state, `BuilderToolsUserData`, needs none of that — its
`onEntityRemoved` is deliberately empty (`BuilderToolsUserDataSystem.java:28`), because the
component travels with the detached `Holder` and is garbage-collected with it.

### Why not `PlayerDisconnectEvent`

It exists (`server/core/event/events/player/PlayerDisconnectEvent.java:7`) and it is fine, but
it fires only on "left the server". It misses world switch and world crash, both of which must
end a flight because the drone lives in the world's own `EntityStore`. The ECS hook covers all
of them and cannot be missed. We use no event bus listeners in this ticket at all.

## Design

### Components

| Component | Lives on | Serialized? | Holds |
| --- | --- | --- | --- |
| `FlightSession` | pilot | **no** (`Supplier` overload) | `Ref<EntityStore>` of the drone |
| `ParkedBody` | pilot | **yes** (id + codec) | which body markers *we* applied |
| `DroneComponent` | drone | no | `Ref<EntityStore>` of the pilot |

`FlightSession` is transient on purpose: a session is meaningless across a restart, and a
serialized one would let a pilot relog into a session whose drone no longer exists.
Registration is the `registerComponent(Class, Supplier)` overload, which
`ComponentRegistry.java:292-293` documents as no-id-no-codec, i.e. not serialized.

`ParkedBody` is serialized on purpose, and it is the subtle half of the design — see below.

`DroneComponent` carries the pilot back-reference because #23's flight tick will query drones
and needs the pilot to read input from, and because it lets drone-side removal clean up the
session (below). It is named `DroneComponent` rather than `Drone` to match Hytale's own
`ModelComponent`/`TransformComponent` naming and to leave `Drone` free.

### The `ParkedBody` trick: restore on *add*, not on removal

The pilot's character must become invisible and invulnerable while flying, and come back after.
The naive placement is "restore on the same teardown hook that kills the drone". That is wrong
in two ways.

`Invulnerable` and `Intangible` are **serialized** components
(`EntityModule.java:328,330` register them with id + codec). So a crash mid-flight would leave
the pilot permanently invulnerable — an orphan just as real as a stray drone entity, and one
the Done-when's "leaves nothing behind" plainly covers.

Also, we must not clear a marker the pilot already had for another reason: Creative mode adds
`Invulnerable` (`Player.java:752`).

Both problems have one answer. `ParkedBody` records *which markers we added* and is itself
serialized, so it survives exactly as far as the markers do — they are saved and loaded by the
same mechanism, so either both persist or neither does, and the pair can never disagree.
Restoration then hangs off the pilot entity being **added**, not removed:

- `RestoreParkedBodyOnAdd` is a `HolderSystem` with query `ParkedBody`. On `onEntityAdd` it
  strips whichever markers `ParkedBody` says we added, then removes `ParkedBody` itself.
  `Store.addEntity` re-reads `holder.getArchetype()` before each holder system
  (`component/Store.java:409`), so mutating the holder there is supported — it is what
  `BuilderToolsUserDataSystem.onEntityAdd` does.
- The involuntary teardown path therefore does not restore the body at all. It just has to not
  lose `ParkedBody`, which it doesn't, because the component rides the detached `Holder`. The
  pilot is restored when they are next added to a store — next world, or next login.
- `land()` does it eagerly, through the same code, so a voluntary land needs no round trip.

One mechanism, three cases: land, world switch, crash-then-relog.

### Invisibility: our own tracker-prune system

There is no supported way to hide an entity unconditionally. I checked all six candidates:

- **Removing `ModelComponent`: does not work.** `EntityTrackerSystems.EntityModel`'s query
  *requires* `ModelComponent` (`:488`) and asserts it non-null (`:519`), so the
  `model != null ? ... : null` at `:545` is unreachable. Removing the component means no packet
  is sent at all and the client keeps rendering the last model it was told about. `Model` is
  also absent from every `queueRemove` call site in the tree.
- **`Model` scale 0: does not work.** `0.0F` is the *unset* sentinel — every entity without an
  `EntityScaleComponent` already ships `entityScale = 0.0F` (`EntityTrackerSystems.java:520`).
- **Removing `NetworkId`: works but is not reversible.** `takeNextNetworkId()` hands out a
  *different* id, and `PlayerSystems.sendPlayerSelf` throws
  `"Viewer is missing NetworkId component"` (`PlayerSystems.java:571-573`).
- **An `entityeffect` invisibility effect: does not exist.** `grep -i invisib` over the whole
  tree returns one unrelated hit in `UserMapMarkerConfig`. There is no invisibility status
  effect, no `Invisible` component, and no `ComponentUpdateType` for one.
- **`HiddenPlayersManager`: conditional.** `EntityTrackerSystems.HideFromPlayer:801` gates the
  entire hide loop on `!playerSettings.showEntityMarkers()`, a client-sent preference. `/hide`
  silently no-ops for viewers with markers on.
- **`HiddenFromAdventurePlayers`: conditional.** `HideEntitySystems.java:81` gates on
  `gameMode == Adventure || !showEntityMarkers()`, and `GameMode` has only `Adventure` and
  `Creative`.

What *is* supported is the extension point all three of those use: a system in
`EntityTrackerSystems.FIND_VISIBLE_ENTITIES_GROUP`, ordered `AFTER CollectVisible`, pruning
`EntityViewer.visible` (a `public Set<Ref<EntityStore>>`,
`EntityTrackerSystems.java:682-690`). Three builtin systems do exactly this. `SendPackets`
then emits the despawn for free, because it treats "no longer in `visible`" and "was destroyed"
identically (`:1029-1031`).

So `HideParkedBody` is a near-verbatim copy of `HideEntitySystems.AdventurePlayerSystem`
(`:28-92`) with the gamemode/settings gate dropped and `ParkedBody` in place of
`HiddenFromAdventurePlayers`. **Judgment call, documented:** this reaches into a public mutable
field of an internal class and is the most likely thing in this change to break on 0.6.0. It is
one file, one system, and the blast radius is "the parked body becomes visible" — never a crash
— which is why I took it rather than shipping conditional hiding.

`SystemGroup.validateRegistry` throws for a group from another registry
(`component/SystemGroup.java:36-40`), so the group and dependency set are **constructor
parameters**: the plugin passes `FIND_VISIBLE_ENTITIES_GROUP` and the `AFTER CollectVisible`
dependency, tests pass `null` and an empty set, and the pruning logic stays inside the harness.

### Systems

| System | Base | Query | Does |
| --- | --- | --- | --- |
| `EnsureDroneNetworkSendable` | `HolderSystem` | `and(drone, not(NetworkId))` | assigns `NetworkId`, ensures `NonSerialized` |
| `EndSessionOnPilotRemoved` | `RefSystem` | `FlightSession` | `tryRemoveEntity(drone, REMOVE)` |
| `ClearSessionOnDroneRemoved` | `RefSystem` | `DroneComponent` | clears `FlightSession` off the pilot **and unparks them** |
| `RestoreParkedBodyOnAdd` | `HolderSystem` | `ParkedBody` | restores the markers we applied |
| `HideParkedBody` | `EntityTickingSystem` | `EntityViewer` | prunes parked bodies from `visible` |

`EnsureDroneNetworkSendable` exists rather than the spawn call just adding a `NetworkId`
inline, because the `NonSerialized` marker is the thing that makes `kill -9` safe and it must
not depend on a caller remembering it. The idiom has five precedents:
`MountSystems.EnsureMinecartComponents:95-130`, `ParkourCheckpointSystems.EnsureNetworkSendable:38`,
`ReachLocationMarkerSystems.EnsureNetworkSendable:46`, `SpawnMarkerSystems:133`,
`ItemSystems.EnsureRequiredComponents:37`.

`ClearSessionOnDroneRemoved` is the symmetric guard. Without it, a drone removed by anything
other than us (chunk unload, `/entity remove`) leaves the pilot holding a stale ref, unable to
relaunch. It cannot recurse with `EndSessionOnPilotRemoved`: removing a *component* does not
remove an entity, and `tryRemoveEntity`/`tryRemoveComponent` both no-op on an invalid ref
(`CommandBuffer.java:124-139`, `:243-252`). It does have to tolerate an already-invalidated
pilot ref, because when the pilot goes first, `Store.removeEntity` invalidates the pilot ref at
`:666-681` and only consumes the buffered drone removal at `:686`.

### `FlightSessions` — the service

One class holding `launch` / `land` / `isFlying` / `droneOf`. It is the only place that knows
the invariant "a pilot is flying exactly when they have a `FlightSession`", which is what makes
"launch spawns exactly one drone" a one-line guard rather than a race.

Signature detail worth calling out: `launch` takes the drone's `Model` as a **nullable
parameter**. Resolving it needs `ModelAsset.getAssetMap()`, which needs a loaded asset registry,
which the harness does not have. Passing it in keeps the whole lifecycle inside the test loop
and pushes the one untestable line (`DroneModel.resolve()`) into a separate three-line class.
This is convention 2 — keep computation out of side effects — applied to assets.

Component types arrive through a `FlightComponentTypes` value object with a public
all-args constructor. `FPVDrone.setup()` builds it — that is the caller obtaining types from
the registry, exactly as the convention prescribes; tests build it against the harness registry.

### The pack model

`fpv-plugin/src/main/resources` **is** the asset pack root: `HytaleExtensionDefaults.groovy:63`
conventions `assetPackSourceDirectory` to `src/main/resources`, `PrepareRunServerTask.groovy:49-81`
symlinks it into `run/mods/<Group>_<modId>`, and server-side `AssetModule.java:411-417` treats a
mod jar's root as the pack root. `includes_pack` itself only sets `IncludesAssetPack` in the
manifest (`UpdatePluginManifestTask.groovy:53`) — it creates no directory.

- `Server/Models/FpvDrone.json` — the `model` asset. Asset id is the **filename**;
  `AssetBuilderCodec.decodeAndInheritJsonAsset:67-78` overwrites any `Id` in the body.
  `HitBox` is the only required key (`ModelAsset.java:175-182`, `nonNull` validator).
  `MinScale`/`MaxScale` are pinned to 1.0 because the defaults are 0.95/1.05 and
  `createRandomScaleModel` would give a randomly-sized drone.
- `Common/Items/FpvDrone/FpvDrone.blockymodel` — geometry. Must live under
  `Common/{Characters,NPC,Items,VFX}` or `CommonAssetValidator.MODEL_CHARACTER:36` rejects it.
  Plain JSON; units are 1/16 block. A plus-configuration quad: body, four arms, four rotor
  discs, nine boxes, origin at the centre of mass because that is what the integrator rotates
  about. `unwrapMode: "collapsed"` on every shape, as the debug gizmo does, so a flat-colour
  texture needs no UV authoring.
- `Common/Items/FpvDrone/FpvDrone.png` — a 16×16 flat dark-grey texture, generated from
  `zlib` + `struct` rather than added as a build dependency. Without it `Model.toPacket()`
  falls back to `textures/Unknown.png` (`Model.java:167`).
- `EyeHeight: 0.1` — roughly the top of the body shell, so #19's first-person camera sits on
  the airframe rather than inside it. A guess, and the first thing to adjust if the FPV view
  looks wrong; nothing else depends on it.
- Fallback: `DroneModel.resolve()` falls back to `ModelAsset.DEBUG` when the asset is missing,
  the idiom at `SpawnMinecartInteraction.java:103`. A broken pack gives a visible debug gizmo,
  not an invisible drone.

**The mesh itself cannot be verified by a test** — `AssetRegistry` needs the ~GB `Assets.zip`
and `CommonAssetValidator` resolves paths through `CommonAssetRegistry`, which only exists in a
booted server. But the *silent* failure modes can be, and `DroneModelTest` covers them: a
`Model`/`Texture` path that does not resolve inside the pack, geometry in a directory the
validator rejects, a missing `HitBox`, an asset id that has drifted from the filename,
unpinned scale bounds, and a degenerate box. Those matter because a model asset that fails
validation just yields an invisible drone, which looks exactly like broken physics. Whether it
*looks* like a quadcopter is for #19 or #22 to say.

## Scope boundary against #22

#22 owns `/fpv launch` and `/fpv land`. This ticket ships the service and the systems and
registers them; it does **not** touch `FpvCommand`. That keeps the two changes from colliding
on the same file and keeps the "failure partway through launch does not leave a player
camera-less" ordering question — which needs #19's camera to exist — in the ticket that owns it.

Consequence, stated plainly: the Done-when is verified by harness tests, not by flying. That is
the right loop for it — "hard disconnect mid-flight leaves nothing behind" is a store-removal
assertion, and flying proves the mesh and the packets, which #19/#22 will do anyway.

## Test strategy

37 new tests. Everything ECS-shaped runs in `HytaleEcsHarness` — plain JVM, no server, no
`Assets.zip`.

- launch spawns exactly one drone, and a second launch is refused
- land removes the drone, clears both pilot components, and leaves relaunching possible
- removing the pilot entity with `RemoveReason.UNLOAD` removes the drone — the disconnect,
  kick, world-switch and world-crash path, all four at once, since all four *are* that call
- removing the pilot leaves `ParkedBody` on the outgoing `Holder`, which is what makes a crash
  recoverable
- removing the drone by any other route clears the pilot's session and unparks them, so they
  are never stranded invisible with nothing to fly
- an outdated drone's death does not cancel the session that superseded it
- the drone carries `NonSerialized`, i.e. it cannot be written to a save
- concurrent drones get distinct `NetworkId`s
- `ParkedBody` restores only the markers we added, never one the pilot already had — in both
  directions, and on the add path as well as the land path
- `HideParkedBody` prunes a parked body from a viewer's `visible` set, leaves other entities
  alone, and stops once the pilot lands
- the pack asset's paths resolve, sit in validator-legal directories, and declare a `HitBox`

Four mutants were introduced and confirmed caught by exactly the expected tests: dropping the
drone removal in `EndSessionOnPilotRemoved` (2 failures), dropping the already-flying guard in
`launch` (1), dropping the restore in `RestoreParkedBodyOnAdd` (2), and dropping the
`iterator.remove()` in `HideParkedBody` (1).

Not covered, and why: whether the mesh looks like a quadcopter and whether the pack loads at
all (needs a loaded asset registry), `DroneModel.resolve()` (same), **`launch` with a non-null
`Model`** — so the `ModelComponent`/`BoundingBox` wiring is exercised only by flying, because
constructing a `Model` needs an asset — and anything reaching `World` (the harness's world is
null by design).

## Risks

- `HideParkedBody` depends on `EntityViewer.visible` staying a public mutable set and on
  `FIND_VISIBLE_ENTITIES_GROUP` existing. Highest-breakage item in the change; isolated to one
  system, fails soft.
- The pack model is unverified in-game.
- `launch`/`land` must run on the world thread — `Store.addEntity` calls `assertThread()`
  (`Store.java:361`). Javadoc'd; #22's command must hop via `World.execute` if it isn't already
  on it.
