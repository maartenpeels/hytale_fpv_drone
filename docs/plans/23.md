# #23 — Flight tick system: substep the integrator inside the world tick

Branch `feat/23-flight-tick-system`, off `main` (at `7318baa`, with #16/#17/#18/#34 merged).

Part of #4 (phase 0). This is the ticket that first makes the drone *move*: it runs
`QuadIntegrator` N times per world tick and writes the result onto the drone entity's
`TransformComponent`.

---

## The two problems, and which one is actually hard

The substep loop is five lines. The hard half is that **`:fpv-core`'s input mapping is called by
nothing in production**. #17 shipped `PilotInputMapper`, `LookTrack`, `PilotInputSample` and a
`ClientMovementAdapter` that stops at "a `ClientMovement` in hand becomes a `PilotInputSample`", and
#18 shipped a drone entity with no physics. Nothing reads packet 108, and nothing carries a
`LookTrack` from one packet to the next. Wiring that is this ticket's real content.

That wiring crosses a thread boundary, and the interval it hands the mapper is a decision with a
known wrong answer. Both are below.

---

## The input seam

### Where input comes from

`PacketAdapters` (`server/core/io/adapter/PacketAdapters.java`) is a public static registry invoked
for every inbound packet at `server/core/io/netty/PlayerChannelHandler.java:30`, **before** dispatch
to the packet handler. `registerInbound(PlayerPacketWatcher)` (`:63-72`) wraps a
`BiConsumer<PlayerRef, Packet>` and returns the `PacketFilter` it created.

#17's plan concluded there was no plugin hook for packet 108, having read `JavaPlugin` (34 lines,
no packet API) and found `wishMovement` stored nowhere. The conclusion was wrong; the hook simply is
not on the plugin base class. Recorded here because "check the plugin base class, conclude no API
exists" is a reasonable move that happens to fail on this API.

Four constraints come with it, all read out of `PacketAdapters`:

1. **The handler lists are `static` JVM-global `CopyOnWriteArrayList`s** (`:13-14`), not per-plugin.
   Leak a watcher across a hot reload and every packet is handled twice — which for this feature
   means the *second* registration silently steals the sample slot writes and the drone gets
   double-rate look deltas. `deregisterInbound` **throws** if the handler was never registered
   (`:90-96`), and the deregistration key is the `PacketFilter` the `register*` call **returned**,
   not the watcher. So the returned filter is held in a field.
2. **Returning `true` from a filter swallows the packet** (`:99-101`). The `PlayerPacketWatcher`
   overload always returns `false`, so it is the one used. We must not suppress `ClientMovement` —
   the player's own body still needs it for chunk streaming (#20).
3. **The watcher runs on the netty thread.** `Store` binds to its constructing thread and
   `assertThread()` throws a plain `IllegalStateException` — not a Java `assert`, so `-da` does not
   help. A watcher must not touch the ECS.
4. **Watcher exceptions are caught and logged at SEVERE, not propagated** (`:104-106`). A broken
   watcher degrades silently. So the watcher is kept to "copy fields, write one reference" and
   everything that could throw on a hostile value stays in `PilotInputMapper`, which #17 already
   documented as never throwing on a sample's account.

### The handoff: a concurrent slot per flying pilot

Two options for constraint 3: hop to the world thread with `world.execute(...)`, or write into a
concurrent slot the tick system drains. **Chosen: the slot.**

`world.execute` was rejected because it makes the handoff *per packet* rather than per tick. Packets
arrive at the client's frame rate, so at 30 TPS a 144 FPS client would queue ~5 runnables per tick
that all mutate the same state and only the last of which matters. The slot expresses "latest input
wins" as a data structure instead of as a queue that happens to be drained in order, and it is where
the per-pilot `LookTrack` naturally lives.

```
PilotInputBuffer                 ConcurrentHashMap<UUID, PilotInputSlot>
  offer(uuid, sample)            netty thread. Writes an EXISTING slot only.
  open(uuid) / close(uuid)       world thread. Presence of the key means "this pilot is flying".

PilotInputSlot
  pending : AtomicReference<PilotInputSample>   netty writes, world thread getAndSet(null)s
  held, track, heldSeconds                      plain fields, world thread only
  nextInput(mapper, tickSeconds) -> ControlInput
```

**`offer` writing only existing slots is what makes the map leak-free.** Presence of a key is
maintained by the world thread and means exactly "a drone is flying for this pilot", so a player who
never flies, or who landed an hour ago, occupies nothing. A `computeIfAbsent` here would have grown
one entry per player who ever sent a movement packet.

The key is the pilot's account `UUID`: the watcher gets it from `PlayerRef.getUuid()` (a plain final
field, safe to read off-thread), and the tick system gets the same value from the pilot's
`UUIDComponent`. Verified those agree: `Player.saveConfig` uses `UUIDComponent.getUuid()` as the
player-storage key (`entity/entities/Player.java:303-307`) and `Player.isHiddenFromLivingEntity`
compares it against `PlayerRef`-managed UUIDs (`:648-655`), both with `assert uuidComponent != null`.

`Ref<EntityStore>` was rejected as the key: `Ref` does not override `equals`, gets invalidated on
every world switch, and is not safe to touch from the netty thread.

### Which interval goes to the mapper — the 4× bug

`PilotInputMapper.map(track, sample, dt)` computes the look rate over
`track.secondsSinceSample() + dt`, and `LookTrack`'s javadoc is explicit about why: look samples
arrive at the client's frame rate while `map` is called at the tick rate, so a delta can span several
ticks and dividing it by one tick's `dt` over-reports the rate by the skip factor. #17's self-review
found exactly that bug, with a test pinning the wrong number.

**Decision: `map` is called exactly once per world tick, with `dt` = the tick length, and the
resulting `ControlInput` is held constant across every substep of that tick.**

Three things follow, and each is a rule the slot has to implement:

1. **Not once per substep.** Calling `map` per substep with `substepSeconds` would be the same bug
   with a different multiplier: only the first substep of a tick would see a fresh sample, so the
   other seven would read `hasLook() == false` and return zero pitch/roll — a one-substep spike
   through the rate PID at 8× the tick frequency. Input is a per-tick quantity because the packet
   rate is not the substep rate.
2. **Not `substepSeconds`, and not the wall-clock tick `dt`** — see the next section for why the
   tick length is the configured one.
3. **A tick with no fresh packet must age the track, not re-consume the held one.** This is the
   subtle case. Re-feeding the last sample looks harmless (its look angles now equal the track's, so
   the delta is zero) but `map` answers `LookTrack.at(...)`, which resets `secondsSinceSample` to
   zero. Five quiet ticks followed by a real sample would then divide a five-tick delta by one tick
   — the original bug, reintroduced through the retry path. So the slot feeds
   `held.withoutLook()`, which keeps the wish axes (throttle and yaw hold, as a physical stick
   would) and takes the `track.aged(dt)` branch, accumulating the interval correctly.

`PilotInputSample.withoutLook()` is the one addition this ticket makes to `:fpv-core`'s control
package. It keeps `wishFrameYaw` — that field was already resolved from a real look yaw, and
`resolveFrameYaw` prefers it — so a held sample stays interpretable.

**Staleness cutoff.** Holding the wish axes forever would mean a frozen client (TCP buffered, process
suspended — not disconnected, so #18's teardown does not fire) leaves the drone at whatever throttle
it last had, climbing away. After `MAX_HELD_SECONDS = 0.5` of no fresh packet the slot switches to
`mapper.centred(track, dt)`, which #17 defined as sticks centred and throttle resting at mid-stick.
Expressed in seconds rather than ticks so it does not change meaning at 240 TPS.

## Substepping

### Where the loop lives

`:fpv-core`, as `FlightTick` — a value holding an integrator and a substep count, with
`advance(state, input, tickSeconds)`. Not inlined into the system, because the property the ticket is
graded on is a property of this loop and it should be tested where there is no server:

> Changing the substep count in config changes CPU cost but not how the drone flies.

`advance` divides `tickSeconds` by the substep count rather than taking a substep length. That is
what makes the property true by construction: **total simulated time per tick is `tickSeconds`
regardless of N.** The failure this guards against is the obvious implementation — N substeps of a
fixed 4 ms — under which raising N from 8 to 16 would make the drone fly twice as fast.

Trajectories are not bit-identical across N (different discretisation of the same ODE, which is the
point of substepping), so the test asserts convergence: 1 second of flight at 4, 8, 32 and 128
substeps agrees to a tolerance, and the tolerance shrinks as N grows.

### Which tick length

`tickSeconds = 1.0 / config.getWorldTps()`, fixed at setup — **not** the wall-clock `dt` the ECS
hands `tick`.

Verified what that `dt` is, because it decides the question: `TickingThread.run` computes
`(float) delta / 1.0E9F` from `System.nanoTime()` (`server/core/util/thread/TickingThread.java:54-72`)
and `World.tick(float dt)` passes it straight to `entityStore.getStore().tick(dt)` (`World.java:342-351`).
So it is *real elapsed* seconds — approximately `1/tps`, but larger whenever the server is behind.

Fixed wins on three counts. Decision 3 says "N **fixed** substeps per tick". A GC pause or a
debugger breakpoint cannot then hand the integrator a 2-second step, which matters because #21's
collision runs per substep and a giant substep tunnels through terrain regardless of how many
substeps there are. And it is deterministic, so flight is reproducible from `(state, input)` alone —
the property `:fpv-core` was split out to preserve.

What it costs: if the world's actual TPS disagrees with `WorldTps`, the simulation runs at the wrong
speed — configure 30 and run `/world tps 120` and the drone flies at a quarter speed. That is
precisely the "not a crash, just a drone that flies wrong in a way nobody can point at" failure
CLAUDE.md's world-units section warns about, so it gets a guard rather than a comment: the system
compares the observed `dt` against the configured tick length and logs a WARNING **once**, naming
both numbers, when they differ by more than 2×. Cheap, needs no world access, and turns a silent
time-dilation bug into a log line.

Not done here, deliberately: **the plugin does not call `World.setTps`.** The ticket's done-when says
raising world TPS needs no *code* change, and it does not — `/world tps` exists and `WorldTps` is
read for the sim. Having the plugin force a world's tick rate would be a plugin reaching outside its
own feature to change a world-wide setting, and it needs a world-load hook this ticket has no other
use for. The mismatch warning is what keeps the two honest.

### The seam for #21

`advance` takes an optional `SubstepListener`, called after **every** substep with
`(before, after, dt)` and returning the state to carry into the next one. `SubstepListener.NONE`
passes `after` through.

That is the whole seam, and it is deliberately the smallest thing that cannot be got wrong later:
one method, one call site, and a core test that counts invocations and fails if the listener runs
once per tick instead of once per substep. Returning a `FlightState` is enough for terrain collision
to clamp the drone to the impact point and zero its velocity, which is what a swept-AABB hit
produces.

`FlightTickSystem` takes a `SubstepListener` by constructor injection, `NONE` for now. Two notes for
#21, since guessing its API here would be worse than leaving room:

- **Block queries need the `World`, which the harness does not have.** Putting collision *inside*
  the system would make the system untestable; putting it behind this listener keeps the world reach
  in an injected collaborator and lets tests inject `NONE`. That is convention 2 (split computation
  from side effects) applied to the one place where this feature has to read the world.
- If per-drone state is needed (a crash verdict, an impact normal), widening the constructor
  parameter from a listener to a per-drone factory is a one-line change here, because nothing else
  in the plugin references it.

## ECS design

### Components

| Component | Lives on | Serialized? | Holds |
| --- | --- | --- | --- |
| `DroneFlight` | drone | no | the current `FlightState`, and the pilot's account `UUID` |

One new component. `FlightState` is `:fpv-core`'s immutable `(DroneState, RatePidState)` pair, so the
component is a mutable holder of an immutable value — replaced each tick, never mutated in place.

The pilot `UUID` is cached on the drone rather than looked up through `DroneComponent.getPilot()`
each tick for a specific reason: it is also what closes the input slot when the drone dies, and at
that moment the pilot's `Ref` is routinely already invalid (`DroneComponent.getPilot()`'s javadoc
records why — `Store.removeEntity` invalidates the pilot ref at `Store.java:666-681` before consuming
the buffered drone removal at `:686`). A `UUID` on the drone's own holder cannot go stale.

### Systems

| System | Base | Query | Does |
| --- | --- | --- | --- |
| `EnsureDroneFlight` | `HolderSystem` | `and(drone, transform, not(droneFlight))` | adds `DroneFlight`, seeded from the spawn transform |
| `TrackPilotInput` | `RefSystem` | `droneFlight` | opens the input slot on add, closes it on remove |
| `AdvanceFlight` | `EntityTickingSystem` | `and(droneFlight, transform)` | drains input, substeps, writes the transform |

`EnsureDroneFlight` follows `EnsureDroneNetworkSendable`'s precedent rather than extending
`FlightSessions.launch`: a drone that exists but has no flight state would sit motionless, and that
guarantee should not depend on a caller remembering a line. It runs *inside* `Store.addEntity` —
holder systems are invoked before the entity gets a `Ref` (`Store.java:403-412`) — which is why it
can read the pilot's `UUIDComponent` through the store and still be sure the pilot is alive.

The initial state is `restingAt` the spawn position with the **spawn yaw** applied, not identity: the
drone should start facing where the pilot faced. Pitch and roll are dropped on purpose — a drone
arming already banked would be a surprise.

`TrackPilotInput` queries `DroneFlight`, not `DroneComponent`, precisely because `DroneFlight`
carries the UUID and `HolderSystem`s have already run by the time a `RefSystem` sees the entity.

`AdvanceFlight` writes `TransformComponent` and `HeadRotation` in place. Verified that this is not a
world side effect: `TransformComponent.setPosition`/`setRotation` are plain field assignments
(`modules/entity/component/TransformComponent.java:65,89`); the only world-touching method is
`markChunkDirty`, which asks a `WorldChunk` to mark itself as needing saving — and a drone carries
`NonSerialized`, so there is nothing to save and it is not called. The system therefore runs whole
inside `HytaleEcsHarness`.

Nothing else has to be told the drone moved. `NetworkId` + `TransformComponent` is what makes an
entity network-sendable (`modules/entity/system/NetworkSendableSpatialSystem.java:17`), #18 already
guarantees both, and `TransformSystems.EntityTrackerUpdate` diffs `TransformComponent` against
`getSentTransform()` each tick and queues a `TransformUpdate` for every viewer
(`modules/entity/system/TransformSystems.java:61-92`).

**Ordering:** `AdvanceFlight` must run *before* `TransformSystems.EntityTrackerUpdate`, or the client
sees each position one tick late — 33 ms of latency added to a feature whose whole open question is
whether the latency is tolerable. Expressed as
`SystemDependency(Order.BEFORE, TransformSystems.EntityTrackerUpdate.class)`. Groups are not a
separate scheduling phase — `DependencyGraph.resolveEdges` just folds a group's dependencies into the
same topological sort (`component/dependency/DependencyGraph.java:41-53`) — so a null-group system
can order against a grouped one. The dependency set is a **constructor parameter**, empty in tests,
because `SystemDependency.validate` throws for a system class the registry does not have
(`component/dependency/SystemDependency.java:31-35`) and the harness has no Hytale systems. Same
reason #18 passed `HideParkedBody`'s group in.

### Quaternion to `Rotation3f`

`Quat`'s javadoc says a Euler readout belongs to the plugin, because Hytale's conventions are the
plugin's problem. So `DroneRotation` in `:fpv-plugin`, with a unit test and no harness.

The conversion needs no sign flips, and the reason is worth writing down because CLAUDE.md's
"`Direction`'s signs disagree with `ControlInput`'s on two axes" makes one expect otherwise. That
warning is about `ControlInput`, which is *transmitter* convention (positive pitch is nose-down).
`Rotation3f` and `Quat` are both geometric and both right-handed:

- `Rotation3f.getQuaternion` is `dest.rotationYXZ(yaw, pitch, roll)` and the inverse readout is
  `q.getEulerAnglesYXZ(...)` (`math/vector/Rotation3f.java:235-252`), all JOML right-handed. Confirmed
  by `Rotation3f.transform`, which is `rotateZ(roll).rotateX(pitch).rotateY(yaw)` (`:263-266`).
- `PositionUtil.toDirectionPacket` is `new Direction(rotation.yaw(), rotation.pitch(), rotation.roll())`
  (`server/core/util/PositionUtil.java:26-28`), so `Rotation3f` maps 1:1 onto the wire `Direction`.
- Hytale yaw *is* a right-handed rotation about `+Y`: `Ry(θ)` applied to `(0,0,−1)` gives
  `(−sinθ, 0, −cosθ)`, which is exactly `Vector3dUtil.setYawPitch`. #17's plan established this and
  corrected CLAUDE.md's "opposite to a right-handed yaw about +Y", which is wrong. Not edited into
  CLAUDE.md here — that file has uncommitted local changes and its verified-facts section is
  ask-first. Reported instead, again.
- Core's body axes are `+X` right, `+Y` up, `−Z` forward (`DroneState`'s javadoc), and a right-handed
  rotation about `+X` takes forward to `(0, sinφ, −cosφ)` — nose up for positive φ, matching Hytale's
  positive-nose-up pitch.

So: build a JOML `Quaterniond` from the core `Quat` and read `getEulerAnglesYXZ`. Note the trap that
`Rotation3f`'s constructor is `(pitch, yaw, roll)` while its accessors are named `yaw()`/`pitch()`,
and that `getEulerAnglesYXZ` returns `(x=pitch, y=yaw, z=roll)`.

Gimbal lock at ±90° pitch is inherent — the wire format is three angles — and affects rendering only;
the simulation stays quaternion-based throughout. A drone hovering nose-down will have a jumpy
apparent yaw. Accepted; nothing in the protocol can avoid it.

### Watcher lifetime

Registered as the only statement of `FPVDrone.start()` and deregistered in `shutdown()`. That is a
matched pair, unlike registering in `setup()`: `PluginBase.start0` only reaches `start()` when
`setup()` succeeded and only reaches `ENABLED` when `start()` returned
(`server/core/plugin/PluginBase.java:259-274`), and `PluginManager.shutdown` only calls `shutdown0`
for an `ENABLED` plugin (`PluginManager.java:398`). Registering in `setup()` would leak the watcher
for good on any later setup failure.

## Test strategy

The interesting properties are all in `:fpv-core` or in plain-JUnit plugin classes; the harness
carries only the ECS wiring.

**`FlightTickTest`** — the done-when. Total simulated time per tick is `tickSeconds` for every
substep count; trajectories at 4/8/32/128 substeps converge; `FlightTick`'s internal substep length
equals `FpvConfig.substepSeconds()` for the same numbers, which pins the config helper against the
loop's arithmetic; a listener is invoked exactly `substeps` times per `advance`, and its returned
state is what the next substep integrates from; rejects a non-positive substep count and a
non-finite `tickSeconds`.

**`PilotInputSlotTest`** — the interval, without a server. A look delta spanning four quiet ticks
yields a quarter of the deflection of the same delta in one tick (the 4× bug, pinned); a tick with no
fresh packet holds throttle and yaw while centring pitch and roll; two packets inside one tick give
the newest one's absolute angles differenced over one tick (latest wins, and a high-FPS client gets
no advantage); after the staleness cutoff the sticks centre.

**`PilotInputBufferTest`** — `offer` for a pilot with no open slot is dropped and allocates nothing;
`close` makes subsequent offers no-ops; concurrent offers from another thread are visible to the
draining thread.

**`FlightTickSystemsTest`** — harness. A launched drone gets `DroneFlight` seeded at the spawn
position and yaw; its input slot opens on launch and closes on land and on pilot removal; one tick at
full throttle moves the drone up and writes the new position into `TransformComponent`; one tick at
zero throttle moves it down; the drone's `HeadRotation` tracks its body rotation; a drone whose pilot
sent nothing still ticks (no packet is not an error).

**`DroneRotationTest`** — round-trips through `Rotation3f` for yaw, pitch and roll independently, and
pins the sign of each against the axis convention rather than against itself.

Not covered, and why: whether the drone *feels* flyable (that is #24, and it is the question phase 0
exists to answer); the actual `PacketAdapters` registration (static JVM-global state and a
`GamePacketHandler` that needs a network channel — the watcher is instead a thin class whose
`accept` is called directly in a test); and anything reaching `World` (the harness's world is null by
design, and nothing here reaches it).

## Risks

- **`wishMovement`'s magnitude and frame are still guesses**, inherited from #17. Both are config
  values in `PilotInputMapping` and the failure modes are legible while flying. #24's job.
- **Fixed `tickSeconds` decouples the sim from wall clock.** A world running slower than its
  configured TPS makes the drone fly slow rather than stutter. That is the right trade for a
  deterministic integrator, but it is a real behaviour change under load, and the mismatch warning
  only fires for a *configured* disagreement, not for a server that is merely behind.
- **The staleness cutoff is a guess at 0.5 s.** Too short and a hitching client gets its throttle cut;
  too long and a frozen client's drone flies away. Nothing depends on the exact figure.
- **Gimbal lock at ±90° pitch** will make a nose-down hover look like it is spinning. Inherent to
  sending Euler angles; visible in #24.
- **Watcher registration is JVM-global.** Deregistration is a matched `start`/`shutdown` pair, but a
  hot reload that skips `shutdown()` for any reason gives duplicated input, and the symptom — look
  deltas at double rate — would read as "the mapping sensitivity is wrong" rather than as a leak.
