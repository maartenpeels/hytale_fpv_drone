# Plan — #38 `Vec3.negated()` returns `−0.0` components, breaking record equality

Ticket: [#38](https://github.com/maartenpeels/hytale_fpv_drone/issues/38) · fix

## What the ticket asks for

`new Vec3(1, 0, 0).negated().equals(new Vec3(-1, 0, 0))` is `false`. Negating an exact `0.0`
arithmetically yields `−0.0`, and record equality compares `double` components with
`Double.compare` (JLS 8.10.3), not `==`. `Double.compare(-0.0, 0.0)` is `−1`, so two numerically
identical vectors compare unequal and hash differently.

Axis-aligned unit vectors are exactly the case that trips this, and exactly what #21 (terrain
collision) and #6 (gate crossing) pass around as face normals. The failure mode is a branch that
refuses to fire while the value looks correct in the debugger.

The ticket asks for the fix's *scope* to be chosen deliberately — `negated()` alone, or the
canonical constructor — with the cost measured rather than assumed, and the reasoning recorded in
the code so it does not get "simplified" away. It also asks that `Quat` be checked in the same pass.

## The decision: normalise in the canonical constructor

`negated()` is not the bug, it is one symptom. Every operation that can land on an exact zero can
produce a signed one:

| operation | input | result |
| --- | --- | --- |
| `negated()` | `(1, 0, 0)` | `(−1, −0.0, −0.0)` |
| `scale(-1)` | `(1, 0, 0)` | `(−1, −0.0, −0.0)` |
| `scale(0)` | `(−1, 0, 0)` | `(−0.0, 0, 0)` |
| `cross()` | any parallel pair | mixed signs |
| `Quat.conjugate()` | `IDENTITY` | `(1, −0.0, −0.0, −0.0)` |
| `Quat.rotate()` | axis vector | mixed signs |
| `BodyRates.toBodyAxes()` | `ZERO` | `(−0.0, −0.0, −0.0)` |

Fixing them one at a time is a list that is never finished, and the next operation added to `Vec3`
starts out broken. The canonical constructor is the only place that catches all of them, including
ones not written yet — so that is where it goes.

The cost is the only real argument against, so it was measured rather than assumed.

### Measurement

**Method, so the numbers below are auditable rather than folklore.** Benchmark:
`QuadIntegrator.step` throughput at `dt = 1/240` — the actual hot path at the actual substep rate —
starting from a level hover at rest, which is the state that actually produces the zeros in
question. 4M steps per trial, 12 trials, best-of the last 8 (first 4 discarded as warmup), state
reset periodically so the numbers are not taken on denormals or infinities. Six variants of
`fpv-core/src/main/java` were compiled with `javac` into separate output directories (the module has
dependency-free by decision 10, so this needs no Gradle) and run as separate JVMs, interleaved and
then re-run in a different order to rule out ordering and thermal effects; base and `fixed` repeated
back-to-back agreed to within 0.1 ns.

Machine: this box, JDK 25 (`/usr/libexec/java_home -v 25`), default JVM flags except where noted.
Absolute ns/step are machine-specific; the ratios between rows are the point.

**Not committed.** It is a one-off measurement, not a regression guard — recorded under Risks below
as a known limitation rather than pretended away.

| variant | ns/step | vs baseline |
| --- | --- | --- |
| baseline, no normalisation | 47.90 | — |
| `Vec3` only, `value + 0.0` | 50.32 | +5.1% |
| `Vec3` + `Quat`, `value + 0.0` | 53.22 | +11.1% |
| `Vec3` + `Quat` + `BodyRates`, `value + 0.0` | 56.40 | +17.7% |
| `Vec3` + `Quat` + `BodyRates`, `value == 0.0 ? 0.0 : value` | 70.75 | +47.7% |

Two things fall out of that table.

**The relative cost is real; the absolute cost is not.** Decision 3 runs 8 substeps per 30 TPS
tick, decision 9 targets 4–8 concurrent pilots — so the ceiling is 8 × 8 = 64 steps per tick, and
1920 steps per second. That is **3.07 µs → 3.61 µs per 33.3 ms tick**, i.e. an extra 0.54 µs against
a 33,000 µs budget: **0.0016%**. Even under decision 3's escape hatch — `World.setTps(240)` with 8
pilots, 15,360 steps/sec — it is 128 µs per second of wall clock, 0.013% of one core. The fix is
affordable by roughly four orders of magnitude, so correctness and consistency decide the scope,
not the benchmark.

**The branchless form is worth having anyway.** `value + 0.0` costs less than half what
`value == 0.0 ? 0.0 : value` does — +17.7% against +47.7% over the same baseline, both measured on
all three records, so it is a like-for-like comparison. Both are correct; one is cheaper for no loss.

*Measured, and separately, reasoned:* the two figures are measurements. The **explanation** for the
gap — that the compare-and-select is what stops C2 from scalar-replacing these short-lived records,
whereas a bare add does not — is inference from the shape of the result, not something confirmed
against JIT output. It is a plausible reading of a 2.7× gap on a record-allocation-dominated
workload, and nothing in the decision rests on it: the choice follows from the measured numbers
either way.

### Why `value + 0.0` is exactly the right operation

IEEE 754 makes it the identity function *except* on the one input we want changed:

- `−0.0 + 0.0 = +0.0` — the case being fixed
- `+0.0 + 0.0 = +0.0` — unchanged
- `x + 0.0 = x` **exactly** for every non-zero finite `x`, subnormals included: the exact sum *is*
  `x`, which is representable, so there is no rounding step to lose anything in
- `±∞ + 0.0 = ±∞`, `NaN + 0.0 = NaN` — non-finite inputs survive, so `isFinite()` still works, and
  record equality already treats every `NaN` as equal to every other via `doubleToLongBits`

It is also, unlike the conditional, verifiably branch-free.

The one hazard is that `x + 0.0` *reads* like dead code, which is precisely the "next person
simplifies it away" risk the ticket calls out. Hence a named helper with the reasoning in its
javadoc, rather than a bare `+ 0.0` repeated at ten call sites with ten drifting comments.

### JIT safety, checked rather than assumed

Neither idiom is any use if HotSpot folds it away. C2 does have identity folding for float adds and
conditional moves, and whether it is guarded against signed zero is not something to recall from
memory. So it was checked: both idioms, and both in bare-method and inside-a-record-constructor
form, run 200M times under `-XX:-TieredCompilation` (forcing C2, no interpreter or C1 fallback to
hide behind), with every result bit-checked via `doubleToRawLongBits`. **Zero failures out of
8×10⁸ checks.** The equality property `negated().equals(...)` was asserted at the end too.

Two committed tests keep this from having to be re-derived — `SignedZeroTest.UnderJitCompilation`
and `Vec3Test.SignedZero.holdsUnderJitCompilationRatherThanOnlyWhenInterpreted` — at 2M and 1M
iterations respectively, enough to get the call sites compiled without slowing the suite (it still
runs in ~1s). `SignedZeroTest`'s version *computes* its `−0.0` as `0.0 * -(i % 5 + 1)` rather than
writing the literal, so constant folding at the call site cannot make it pass for the wrong reason,
and it asserts the premise (that the input really was `−0.0`) as well as the conclusion.

## Scope: three records, not one, and not all of them

`Vec3`, `Quat` and `BodyRates` each get the treatment. `Vec3` is the ticket. `Quat` the ticket asks
to be checked, and it has the bug — `Quat.IDENTITY.conjugate().equals(Quat.IDENTITY)` is `false`,
and `conjugate()` is on the hot path via `inverseRotate`.

`BodyRates` is a deliberate, documented extension of the ticket's scope rather than a silent one. It
is the third record in the same family: three `double` components, its own negating and scaling
arithmetic, and a canonical `ZERO` that callers compare against. The repo already contains a
workaround for it — `BodyRatesTest.zeroRatesMapToAZeroAxisVector` asserts componentwise with the
comment *"negating 0.0 yields −0.0 and record equality distinguishes the two"*. Leaving one of three
known instances of a bug whose whole point is "fix the root cause so callers do not each have to
know" would just recreate the ticket. It is five lines, and the measurement above already covers it.

**Stopping there is also deliberate.** The line is: **a value record that does its own sign-flipping
arithmetic and has a canonical constant callers compare against.** `TorqueDemand`, `PidState`,
`MotorThrusts`, `MotorOutputs` and `RatePidState` are plain carriers — none defines negating or
scaling arithmetic of its own. They hold *signals*, where zero is a magnitude rather than a
direction. If one later grows a `negated()`, it joins the list.

### The rule was applied exhaustively, not just where convenient

All **27** records in the repo (26 in `:fpv-core`, 1 in `:fpv-plugin`) were audited against that rule
by a second pass done independently of the implementation. **No record other than `Vec3`, `Quat` and
`BodyRates` satisfies both halves** — nothing in the repo defines its own negation, scale, cross or
conjugate over `double`/`float` components. Nothing that meets the rule was left alone.

Three near-misses are worth recording, because they are the places a future change could pull into
scope:

- **`TorqueDemand`** — has `NONE`, but no arithmetic of its own, so it fails (a). Its producer
  `RatePid.axis` uses `Math.clamp`, which *preserves* `−0.0` (unlike `MotorMixer`'s clamp to `[0, 1]`,
  which cannot emit one). A `TorqueDemand` holding `−0.0` is reachable only through a degenerate
  all-zero-gain tune, and nothing compares a computed one against `NONE`. Noted, not fixed.
- **`PilotInputSample`** — `ClientMovementAdapter` copies `wishMovement` components straight from the
  client, so a client sending `−0.0` produces a sample unequal to `EMPTY`. `EMPTY` is compared with
  `assertEquals` in tests but nothing in main code branches on it (`PilotInputMapper` uses
  `Double.isFinite`). The only spot where *external* input can create the mismatch. Noted, not fixed.
- **`ControlInput`** — `float`, and fails (a): its zeros come from the wire, not from its own
  arithmetic. The `−0.0f` really is produced, by `PilotInputMapper`'s rotation and negations, and it
  is already scrubbed there by `PilotInputMapper.stick`, documented and covered by
  `PilotInputMapperTest.neverEmitsANegativeZeroBecauseItWouldCompareUnequalToACentredInput`.

That last one means the codebase now handles this hazard two ways: normalisation inside the type
(`Vec3`/`Quat`/`BodyRates`, plus `Contact`'s bare `entryTime`) and scrubbing at the producer
(`PilotInputMapper.stick`). That is **left as is, deliberately.** `stick` is `float` while
`SignedZero` is `double`, so routing it through would mean adding an overload purely to relocate a
working, tested, documented three-line method; and scrubbing at the producer is the right shape for a
type that never creates a signed zero itself. The two mechanisms are cross-referenced from
`SignedZero`'s javadoc so they read as one family rather than a contradiction.

## #16's boundary workaround: half stays, half goes

`SweptResult.Contact`'s constructor currently collapses `−0.0` in two independent places. They get
opposite verdicts, which is the point of looking at them separately rather than as one "workaround".

**The normal block goes.** Once `Vec3`'s constructor cannot hold a `−0.0`, `new Vec3(zeroed(x),
zeroed(y), zeroed(z))` is code that provably cannot change its input. That is worse than no code: it
cannot be tested (any test for it passes vacuously), and by existing it asserts that `Vec3` is
unsafe — which is exactly the belief that would make the next person re-add the same three lines at
the next boundary. Defence in depth is a real argument where the second layer can independently
fail; here it cannot fail, it can only mislead. The `zeroed` helper goes with it.

**The `entryTime` line stays.** `entryTime` is a bare `double` component of `Contact`, not a `Vec3`,
so nothing upstream can canonicalise it and `SweptAabb` genuinely can compute it as `−0.0` (an exact
zero divided by a negative travel). It is not duplication of the `Vec3` fix; it is the same class of
bug in a place the `Vec3` fix does not reach. It gets rewritten to call `SignedZero.canonical` so
there is one explanation of the hazard instead of two.

The tests on both — `SweptResultTest` and `SweptAabbTest.SignedZero` — all stay. They assert
`Contact`'s public contract ("the normals this hands out are free of `−0.0`"), which is still true
and still worth pinning regardless of which layer now implements it; `SweptAabbTest.SignedZero` in
particular sweeps every axis and sign combination, which is real coverage of the new constructor
reached through a real caller. Only the comments explaining *where* the guarantee comes from change.

## Behavioural risk: does killing `−0.0` change any answer?

Normalising in a constructor is a global behaviour change, so the ways `−0.0` can be load-bearing
were checked rather than waved at. The dangerous pattern is `1/x`, where `−0.0` gives `−∞` and
`+0.0` gives `+∞`.

- **`SweptAabb.sweep`** divides by `travel`, a displacement component. Safe: `travel == 0.0` is
  tested *first* and catches both signs, so a signed zero never reaches a division. The subsequent
  `travel > 0.0` / else split is only reached for genuinely non-zero travel.
- **`Vec3.normalised()`, `Quat.normalised()`** divide by a length, which comes from `sqrt` and is
  never `−0.0`.
- **`Aabb`** compares components with `>` and `<` (`min.x() > max.x()`, `value.x() < 0.0`). Both
  already treat `−0.0` and `0.0` alike, so its validation is unchanged.
- **`Math.copySign` in `RateCurve`, `Math.signum` in `RatePid`** operate on `double`s that never came
  through one of these three records.
- No `−0.0` literal exists anywhere in `fpv-core/src/main` or `fpv-plugin/src`, so nothing is
  written expecting one.

Nothing depends on the sign of a zero surviving.

## Test strategy

A `@Nested SignedZero` group on each of `Vec3Test`, `QuatTest` and `BodyRatesTest`, asserting the
ticket's "done when" directly: the result of a sign-flipping operation on a zero component is
`equals` **and** `hashCode`-consistent with the same value built from literals. `hashCode` is
asserted explicitly and not treated as implied — the ticket names it, and a `Set`/`Map` caller is the
scenario, so it earns its own assertion.

Bit-level assertions via `Double.doubleToRawLongBits` alongside the `equals` ones, because
`assertEquals(0.0, -0.0)` passes for `double` and would hide the very thing being tested.

`SignedZeroTest` pins the helper itself, including the cases that make the one-line body correct
rather than incidental: non-zero values are returned bit-identically, subnormals survive, `±∞`
survives, `NaN` survives. Those are the tests that fail if someone replaces the body with
`return value;`.

Existing tests are the other half of the strategy: every core test across the integrator, PID, rate
curves and swept AABB must pass unchanged. `SweptAabbTest.SignedZero` and `QuatTest`'s integration
drift tests are the ones with real power to catch a mistake here.

## Risks

- **Low.** The change cannot alter any arithmetic result, only the sign bit of results that are
  already zero, and every consumer of that sign bit was enumerated above.
- **Performance**, quantified above and accepted with four orders of magnitude of headroom. The
  benchmark is a one-off and is not committed, so a future regression here would not be caught
  automatically — recorded as a known limitation rather than pretended away.
- **A reader deleting `+ 0.0` as dead code.** Mitigated by the helper's javadoc and by
  `SignedZeroTest`, which fails if the body becomes `return value;`.

## Out of scope

- **`ControlInput`** — `float` components clamped from packet data. Same theoretical hazard, but its
  zeros come from a wire format rather than from sign-flipping arithmetic, and it has no negating
  operation. Not touched.
- **`:fpv-plugin`** — constructs no `Vec3` or `Quat` at all today (verified by grep), so there is
  nothing to adapt at the boundary.
- **CLAUDE.md** — has uncommitted local edits; left alone.
