# 34 — Test harness for `:fpv-plugin`: ECS unit tests without a server

Issue: #34 (part of #4). Unblocks the testability of #18, #21 and #23.
Milestone: v0.1 — Feel.

## Problem

`CLAUDE.md`'s Tests section records `:fpv-plugin` has no tests — adapters are verified by
flying. That was a settled position, and it is why every plugin-side phase-0 ticket has no
feedback loop at all: an adapter either compiles or it does not, and everything past that is
discovered by launching a server and flying.

It turns out to be false. Hytale's ECS is drivable in a plain JVM: `ComponentRegistry` has a
public no-arg constructor that pulls in no world, no scheduler, no network and no assets, and
`Store.tick(float)` is public. So a plugin-side system *can* be unit-tested — provided the
system is written so that it is testable, which is the real deliverable here.

## Goal

Two things, in order of importance:

1. **Establish the constructor-injection convention** for `ComponentType`, so #18, #21 and #23
   are written testable from the first commit rather than retrofitted. This is trap 1 below and
   it is the reason the ticket exists.
2. **Wire a JUnit test source set into `:fpv-plugin`** with a reusable harness and one
   proof-of-life test, so the convention has something to be verified by.

Two additional facts read while planning, not in the issue body:

- **`Store.tick` calls `registry.doDataUpdate()`** (`Store.java:1677`), which flushes pending
  registrations. So registering a system *after* the store exists still works. The harness does
  not need to force a register-then-create-store order.
- **`Store.addEntity` calls `assertWriteProcessing()`** (`Store.java:362`), which throws only
  when processing is already held — i.e. only when called from inside a system tick
  (`Store.java:/assertWriteProcessing/`). Top-level test code is fine. The corollary constrains
  #18/#23: a system must mutate the world through its `CommandBuffer`, not by calling
  `store.addEntity` / `store.removeEntity` from inside `tick`.

## Approach

### Build wiring — `fpv-plugin/build.gradle.kts`

Normally an ask-first path per `CLAUDE.md`. Explicitly approved for this ticket.

1. JUnit 5 via the same `junit-bom` version `:fpv-core` already pins (5.11.4), so the two
   modules cannot drift. The root `build.gradle.kts` already applies `useJUnitPlatform()` to
   every subproject `Test` task, so no test-framework config is needed here.
2. Put the server jar on the test compile+runtime classpath:
   `testImplementation(files(configurations.named("vineServerJar")))`. `files(...)` rather than
   `extendsFrom` because `vineServerJar` is a resolvable configuration, not a dependency
   bucket — `compileOnly.extendsFrom(vineServerJar)` is how the Hytale plugin itself consumes
   it, but a `Test` task needs the jar on the *runtime* classpath too, and `compileOnly` by
   definition is not.
3. **Mandatory JVM arg**, without which the harness cannot run at all:
   `-Djava.util.logging.manager=com.hypixel.hytale.logger.backend.HytaleLogManager`.
   Setting the property from inside a test is too late — `LogManager` is already initialised.
4. **Do not enable JUnit parallel execution**, and say why in a comment, because `Store` is
   thread-bound.

### The harness — `EcsHarness`

A small `AutoCloseable` test fixture in the test source set:

- owns a fresh `ComponentRegistry<EntityStore>` per instance — never
  `EntityStore.REGISTRY` (trap 3),
- creates its `Store<EntityStore>` via `addStore(externalData, EmptyResourceStorage.get())`,
- `close()` calls `registry.shutdown()` (trap 4).

**Judgment call — `ECS_TYPE` is `EntityStore`, with a `null` `World`.** The alternative was a
synthetic marker type, which would make the harness self-contained but useless: our real
systems are `EntityTickingSystem<EntityStore>`, so a harness parameterised on anything else
could not instantiate the very classes #18/#23 need to test. `EntityStore`'s constructor
(`EntityStore.java:52-54`) only assigns the `World` field; `getWorld()` is the sole
dereference. So `new EntityStore(null)` is a valid external-data object for any system that
does not reach for the world — and reaching for the world is exactly what trap 6 already tells
us to keep out of computational systems. The `null` is therefore load-bearing in a useful
direction: **if a system under test touches the world, the test NPEs, which is the harness
telling you the system has mixed computation with side effects.** Documented in the harness
javadoc so the NPE is diagnosable rather than mysterious.

Residual risk, to be settled empirically: `EntityStore`'s static initialiser builds the global
`REGISTRY` and a `SEND_PACKET_GROUP`, and registers a codec supplier. That is class-init work we
trigger but do not use. If it throws in a bare JVM, fall back to a synthetic `ECS_TYPE` and
record the loss of fidelity here.

### Proof-of-life test

One `EntityTickingSystem` over one trivial component: create entity, `store.tick(dt)`, assert
the component was mutated and that `dt` arrived intact. The system takes its `ComponentType`
by constructor injection — it is the executable example of the convention, not just a test.

### Encoding trap 1 as a test

Beyond the proof of life, assert that `TransformComponent.getComponentType()` really does fail
outside a booted server. This pins the *reason* for the convention: if a future Hytale release
makes it safe, that test fails and someone re-reads this decision deliberately instead of the
convention quietly becoming cargo cult.

### `CLAUDE.md`

- **Tests section**: replace the `:fpv-plugin` has no tests claim. Record what the harness can
  and cannot do, and the mandatory JVM arg.
- **Conventions section**: add the constructor-injection rule as a project convention, stated
  strongly enough that a later agent cannot miss it — this is the ticket's primary output.

## Test strategy

The harness *is* test infrastructure, so "tests for the tests" would regress into nothing. What
the proof-of-life test actually pins is the harness's own contract: registry constructs, store
constructs, entity is created, a registered system observes it, `tick` propagates `dt`, and
teardown does not hang. If Hytale breaks any of that in a future release, this test is the
canary — which is most of its value, given the API is decompiled and pinned `>=0.5.3 <0.6.0`.

## Risks

- **The JVM arg is invisible until it is missing.** A developer adding a *new* `Test` task, or
  running a test from an IDE that does not read Gradle's `jvmArgs`, gets
  `IllegalStateException: Log manager wasn't set!` with no obvious link to this decision. The
  comment in `build.gradle.kts` names the symptom so the error text is greppable.
- **Thread-bound `Store` vs. future parallelism.** If anyone enables JUnit parallel execution
  later for speed, these tests fail confusingly. Comment says so at the point of temptation.
- **`null` `World`.** Deliberate (see above), but it does mean the harness cannot test anything
  world-touching. That is a scope boundary, not a defect — issue #21's block lookup will need a
  different approach, and the issue already anticipates that with the collision differential
  oracle.

## BLOCKER — the build wiring is not in this branch

**Status: the one change this ticket cannot be finished without was denied by the permission
system, so this branch does not build.** `fpv-plugin/build.gradle.kts` is an ask-first path in
`CLAUDE.md`; the edit was attempted and refused, and there was no interactive session in which
to grant it. Everything else is done and verified.

The harness itself is *not* speculative — it was compiled and executed against the real
`Server-0.5.9.jar` outside Gradle (see Evidence below), so the only missing piece is Gradle
wiring. Apply this hunk to `fpv-plugin/build.gradle.kts` and the branch is green.

Replace the existing `dependencies { ... }` block with:

```kotlin
dependencies {
    implementation(project(":fpv-core"))
    bundledCore(project(":fpv-core"))

    // Hytale's ECS is drivable in a plain JVM -- no server boot, no Assets.zip, no client.
    // See docs/plans/34.md for what that does and does not make testable.
    //
    // The server jar has to be put on the test classpath by hand: the Hytale Gradle plugin
    // wires `vineServerJar` into `compileOnly` only (HytaleConfigurationConfigurer.groovy:66)
    // and has no test support of any kind. `files(...)` rather than
    // `testImplementation.extendsFrom(vineServerJar)` because a Test task needs the jar on the
    // RUNTIME classpath too, and `compileOnly` by definition is on no runtime classpath.
    // `vineServerJar` is declared `canBeResolved = true` (same file, :30), which is the hook.
    testImplementation(files(configurations.named("vineServerJar")))

    // Same junit-bom version as :fpv-core, so the two modules cannot drift.
    testImplementation(platform("org.junit:junit-bom:5.11.4"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.named<Test>("test") {
    // MANDATORY -- without this no ECS test can even load its own imports.
    //
    // ComponentRegistry holds a `static final HytaleLogger` (component/ComponentRegistry.java:76),
    // and HytaleLogger's static block (logger/HytaleLogger.java:112-126) throws
    //     IllegalStateException: Log manager wasn't set!
    // unless the JUL log manager was replaced at JVM startup. Calling System.setProperty from
    // inside a test is too late: java.util.logging.LogManager has already initialised.
    //
    // If you see that exception, you are running these tests on a JVM that did not get this
    // flag -- a hand-rolled Test task, or an IDE runner that ignores Gradle's jvmArgs.
    jvmArgs("-Djava.util.logging.manager=com.hypixel.hytale.logger.backend.HytaleLogManager")

    // Do NOT enable JUnit parallel execution here. `Store` binds to its constructing thread
    // (component/Store.java:106) and assertThread() (:1992-1997) throws a plain
    // IllegalStateException -- not a Java `assert`, so -da will not help -- from any other
    // thread. Parallel execution turns these tests into confusing intermittent failures.
}
```

Nothing else changes: `gradle.properties`, `settings.gradle.kts` and the root
`build.gradle.kts` are untouched, and the root already applies `useJUnitPlatform()` to every
subproject `Test` task.

## Evidence

`./gradlew :fpv-plugin:test` has **not** been run, because of the blocker above. Instead the
harness and its tests were compiled and executed directly against the cached server artifact
`~/.gradle/caches/modules-2/files-2.1/com.hypixel.hytale/Server/0.5.9/.../Server-0.5.9.jar`,
with JUnit 5.11.4 taken from the same Gradle cache, on JBR 25.0.4:

- `javac` against the server jar: **clean, no errors and no warnings.**
- With the log-manager flag: **5 tests found, 5 succeeded, 0 failed** (124 ms).
- Without the log-manager flag: **5 tests found, 0 succeeded, 5 failed**, every one
  `ExceptionInInitializerError` caused by
  `IllegalStateException: Log manager wasn't set! ... Log manager is: java.util.logging.LogManager@...`.

That last pair is the useful one: it proves the mandatory JVM arg is genuinely mandatory rather
than defensive, in both directions.

Also confirmed by the run, since these were the real risks in this plan:

- `new ComponentRegistry<EntityStore>()` and `addStore(new EntityStore(null), EmptyResourceStorage.get())`
  work in a bare JVM. `EntityStore`'s static initialiser — which builds the global `REGISTRY`,
  a `SEND_PACKET_GROUP` and a codec supplier — does not throw. The fallback to a synthetic
  `ECS_TYPE` contemplated above is **not needed**.
- `Store.tick(float)` really does invoke a constructor-injected `EntityTickingSystem` over a
  matching entity, and `dt` arrives unmodified.
- `TransformComponent.getComponentType()` really does throw `NullPointerException` outside a
  booted server. Trap 1 is real, which is the whole basis for the constructor-injection
  convention.
- `registry.shutdown()` in teardown does not hang the JVM.
