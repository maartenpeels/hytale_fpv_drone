# Plan — #45 Centre stick commands 50% throttle, but hover is at 35%

Ticket: [#45](https://github.com/maartenpeels/hytale_fpv_drone/issues/45) · fix · milestone v0.1 — Feel

## What the ticket asks for

Found on the first real flight. With no key held, the drone climbs away and never stops.

`PilotInputMapper` maps `throttle = (forward + 1) / 2`, so a centred stick asks for `0.5`. Motor
thrust goes with the *square* of the command, so on the default airframe
(`thrustToWeight = 8.0`, `gravity = 32.0`) hover is at

```
hoverCollective() = sqrt(1 / 8) = 0.35355…
```

and `0.5` produces `8 × 32 × 0.5² = 64` against a weight of `32` — a sustained 1 g climb. The
physics is right; the mapping is wrong.

The fix is to make centre stick command *hover*, piecewise so both endpoints stay pinned:

```
forward >= 0 :  throttle = hover + forward * (1 - hover)
forward <  0 :  throttle = hover * (1 + forward)
```

## Where the hover point lives, and why not on `PilotInputMapping`

The ticket suggests a new field on `PilotInputMapping` whose default derives from
`QuadParameters.DEFAULT_THRUST_TO_WEIGHT`. That derivation is the important half and it stays; the
*placement* does not, for two reasons.

**1. It would close a package cycle.** `com.maartenpeels.fpv.flight` already depends on
`com.maartenpeels.fpv.control` — `QuadIntegrator` and `FlightTick` both import `ControlInput`, and
that direction is the data flow: sticks feed the flight model. `control` currently imports nothing
from any other `fpv` package; it is a leaf. Having `control.PilotInputMapping` import
`flight.QuadParameters` would make the two packages mutually dependent, which is exactly the kind of
knot decision 10 is trying to keep out of `:fpv-core`.

**2. `PilotInputMapping` is device calibration, not airframe.** Its own javadoc says so — "what
counts as full stick deflection", "per-pilot", and the place decision 11's calibration wizard will
eventually write to. Where hover sits is a fact about the *frame*, server-wide, and it moves when the
airframe is retuned rather than when the pilot swaps sticks. `QuadParameters`' javadoc draws the same
line and gives the reason: full-stick rate moved *out* of the airframe record in #15 because it is a
tune, not a frame property. This is that boundary in the other direction.

So the hover throttle becomes a second constructor parameter on `PilotInputMapper`, and the
composition root derives it from the airframe it is already building:

```java
QuadParameters airframe = QuadParameters.DEFAULT;
new FlightTick(new QuadIntegrator(airframe), substeps);
new PilotInputMapper(PilotInputMapping.DEFAULT, airframe.hoverCollective());
```

That is strictly stronger than deriving from `DEFAULT_THRUST_TO_WEIGHT`: it binds the mapping to the
airframe *actually being flown*, so a non-default airframe (#5's per-pilot tunes) can't drift from
its own hover point either. Types differ (a record and a `double`), so the two arguments cannot be
transposed and still compile.

Cost: every `PilotInputMapper` construction site has to be updated — one in production, the rest in
tests. Accepted: that is churn, not coupling.

## The airframe that cannot hover

`hoverCollective()` returns more than `1` when `thrustToWeight < 1`, deliberately, and its javadoc
hands the problem to us: "callers turning this into a `ControlInput` throttle need to handle the
case." Three options:

- **Clamp to 1.** Hides a broken tune behind a drone that flies almost normally.
- **Let it through.** Worse than it looks: with `hover > 1` the `forward >= 0` branch has a
  *negative* slope, so pushing the throttle stick forward would reduce thrust. An inverted control is
  a worse failure than no control.
- **Reject it at construction.** Chosen.

`PilotInputMapper` requires `hoverThrottle` to be finite and within `(0, 1]`. An airframe that cannot
lift its own weight cannot be flown by any mapping, so there is no correct mapper to build for it,
and the loudest available response is to refuse once at wiring time rather than to fly wrong on every
tick. This is consistent with the mapper's existing split: an untrusted *sample* never throws, but
`dt` — which comes from our own tick loop — does. The hover throttle comes from our own airframe
config, so it throws. `thrustToWeight == 1.0` exactly is allowed: hover at full stick is degenerate
but coherent, and the descending half of the travel still works.

## Test strategy

The bug escaped a suite of ~400 tests because every throttle assertion restated the mapper's own
constant. The tests that matter here are the ones that check the mapping against the *airframe*.

1. **Physical, in `PilotInputMapperTest`** — a new `@Nested` group that wires the real
   `PilotInputMapper`, `QuadIntegrator` and `FlightTick` on `QuadParameters.DEFAULT`, feeds one
   input for a simulated second at 30 TPS × 8 substeps, and asserts on altitude:
   - centre stick (`PilotInputSample.EMPTY`) holds altitude within a tight tolerance;
   - full forward climbs by a large margin;
   - full back cuts the motors and falls at roughly free-fall.
2. **The tolerance is pinned as non-vacuous** by a test in the same group that flies a literal
   `0.5f` throttle through the same rig and asserts it climbs *past* the hover tolerance by orders
   of magnitude. That test is the regression guard: reverting the centre to mid-scale fails both it
   and the hover test.
3. **Existing `0.5`-at-centre assertions are corrected, not deleted**, and renamed to say *hover*
   rather than *mid-stick* — the old names asserted the bug in prose as well as in numbers.
4. **Endpoints and the piecewise slopes** get their own cases, including half-stick each way
   (`hover + 0.5·(1−hover)` and `0.5·hover`), so the two branches are covered independently.

## Measured

One second of simulated flight from rest, `QuadParameters.DEFAULT`, 30 TPS × 8 substeps, altitude in
world units:

| throttle | altitude after 1 s |
| --- | --- |
| hover (`0.35355338`, what centre now commands) | `−5.3e-7` |
| `0.5` (what centre used to command) | `+14.82` |
| `1.0` | `+83.68` |
| `0.0` | `−14.82` |

So the hover tolerance of `0.01` has four orders of margin on the correct value and is exceeded ~1500×
by the old one. Verified by reverting the mapper to `(forward + 1) / 2` and re-running: 20 tests fail,
including `holdsAltitudeForASecondWithTheStickCentred` — *expected `<0.0>` but was `<14.816…>`* — and
`holdsAltitudeOnAnAirframeWithADifferentThrustToWeight`, which fails in the opposite direction
(`−3.84`, mid-scale being *below* hover on a `thrustToWeight = 3` frame). Two independent airframes
disagreeing with the same constant is what makes that pair a real check rather than a restatement.

## Risks

- Half-stick numbers are no longer `0.75`/`0.25`, so a few `wishFullScale` scaling assertions need
  recomputing against the new curve. Mechanical, but easy to "fix" by copying whatever the code
  prints — the new expectations are written as expressions over `hover`, not as decimals.
- `float` narrowing: `(float) sqrt(1/8)` is `0.35355338…`, so `collective` is off from `0.125` by
  ~4e-9 and the drone accumulates ~1e-6 u/s of climb over a second. Far inside any sane tolerance,
  but it is why the hover assertion is a tolerance rather than an equality.
- Nothing here touches Hytale, so `:fpv-core` stays free of `com.hypixel.*` (decision 10).
