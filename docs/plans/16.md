# Plan — #16 Swept segment/AABB routine in `:fpv-core`, shared with gates

Ticket: [#16](https://github.com/maartenpeels/hytale_fpv_drone/issues/16) · Epic: #4 · Milestone: v0.1 — Feel

## What the ticket asks for

One routine, in `:fpv-core`: given the drone's box and the segment from last-tick position to
this-tick position, does it intersect a given box — and if so, *where* and with *what normal*.

Done when tests cover: a clean miss, a face hit with the correct normal, a **fast pass that would
tunnel under a containment test**, a glancing edge case, and a start-already-overlapping case.

## Two callers, and what each one actually needs

This is the constraint that shapes the return type. Decision 6 says the gate crossing test reuses
this routine, so the answer has to serve both without either caller inventing information.

| | #21 terrain collision | #6 gate crossing |
| --- | --- | --- |
| Question | did I hit a block? | did I pass the gate, the right way? |
| Needs the time of impact | yes — to place the drone at contact | not really |
| Needs the normal | yes — to resolve the crash | **yes, and signed** — it *is* the direction test |
| Needs the exit time | to know it ended embedded | to know the pass *completed* inside the tick |
| Needs "already overlapping" | yes — spawned in terrain, or last tick's resolution failed | yes — the pass was already in progress |
| Boxes are axis-aligned in world space | yes (blocks) | **no** — gates have orientation |

The last row is the one that could have forced a much harder routine. It does not, and the reason
is worth writing down: **a rotated gate is handled by the caller transforming the segment into the
gate's local frame**, where the gate *is* axis-aligned, running this routine, and rotating the
returned normal back. For a box under a rigid rotation that is exact, not an approximation. So this
routine stays axis-aligned, and #6 pays one quaternion conjugation per gate.

The drone's own box is treated as **world-axis-aligned and non-rotating**. A quad's attitude changes
its true silhouette, but sweeping a *rotating* box is a materially harder problem (no closed-form
time of impact) and "crash into terrain" does not need it. Stated as a judgement call, not an
oversight; a slightly generous box is the conventional choice and the one Minecraft-lineage servers
make.

## Design

### The reduction: Minkowski expansion, then the slab method

Box-vs-box sweep under pure translation reduces *exactly* to segment-vs-box: grow the target by the
mover's half-extents, shrink the mover to its centre point, and the two problems have the same
answer at the same times. So:

1. `expanded = target.expandedBy(mover.halfExtents())`
2. ray from `mover.centre()` along `displacement`, parameter `t` where `t = 0` is last tick and
   `t = 1` is this tick
3. per-axis slab intersection, tracking `entry = max(axisEntry)` and `exit = min(axisExit)`

This is the standard approach and it is what makes the routine tunnel-proof by construction:
`entry` is a solved time, not a sampled one, so a 20-unit step through a 1-unit wall is found the
same way a 0.02-unit step is.

### The rule that decides every edge case: overlap must have positive measure

Rather than scatter epsilons, the routine follows one rule: **an intersection is a non-empty *open*
interval of genuine overlap inside `(0, 1)`.** Every awkward case falls out of it, consistently:

| Case | Falls out as | Why that is the behaviour we want |
| --- | --- | --- |
| Motion parallel to a slab, exactly tangent to it | miss (strict slab containment) | a drone resting exactly on the floor and sliding along it must not crash every tick |
| Exact corner graze, `entry == exit` | miss | zero duration of contact is not a collision |
| Head-on face hit | contact at the tangency time | this is the *definition* of time of impact, so tangency has to count on the axis of motion |
| Arrives exactly tangent at `t == 1` | miss this tick, contact next tick at `entryTime == 0` | no tunnelling, and no crash on a perfect touch-down |
| Tangent at `t == 0`, moving away | miss | it is leaving |
| Tangent at `t == 0`, moving in | contact, `entryTime == 0` | not yet overlapping, so not `AlreadyOverlapping` |
| Genuinely overlapping at `t == 0` | `AlreadyOverlapping` | there is no face it crossed; see below |
| Zero displacement | pure overlap test | degenerates correctly with no special case |

Note the asymmetry that makes this work: tangency **counts** on an axis the mover is crossing, and
**does not count** on an axis it is parallel to. Both are the same rule — positive-measure overlap
over an interval of time — applied to an axis that varies with `t` and one that does not.

**There is no epsilon and no skin width.** Adding one would be adding a tuning parameter to a
routine whose whole value is that it is exact, and it would push the phantom-crash question into a
constant nobody can reason about. If #21 wants a skin, it belongs there, as a deliberately shrunk
drone box — which is a thing you can look at and understand.

One consequence worth stating, because it is where "grazing must not crash" actually gets decided:
**this routine reports a *contact*, not a *crash*.** A drone resting on the floor with a downward
velocity of `1e-18` is genuinely moving into the floor and does get a `Contact` — correctly, because
that is how landing works. What stops it being a crash is an impact-speed judgement, and that
judgement is #21's, not this routine's. What this routine *does* guarantee is that pure lateral
sliding along a surface — the actual phantom-crash case — is a `Miss`.

### Checked against the server's own evaluator, then deliberately diverged

`MovingBoxBoxCollisionEvaluator`, `CollisionMath` and `RaycastAABB` were read (0.5.9) for approach
and edge cases. Confirmations and divergences, both worth recording since #21 will be calling
Hytale's block lookup right next to this code:

Confirmed — the same choices, arrived at independently:

- Minkowski expansion then per-axis slab times, normalised so `t ∈ [0, 1]` over the frame
  displacement. `CollisionMath.intersectSweptAABBs` does literally this.
- The normal is the **outward** face normal of the struck face, pointing back at the mover.
  `SimplePhysicsProvider` depends on it (`contactNormal.equals(UP)` is how it knows it is grounded).
- One axis, one component, `±1`. Ties on an exact corner approach resolve by strict `>`, so X beats
  Y beats Z. Same rule here, and tested.
- Initial overlap is a **separate outcome**, not a contact with an invented normal. Hytale flags it
  `overlapping` and returns `false` from the collision test; `SimplePhysicsProvider` skips those
  blocks and accumulates a push-out instead.

Diverged, deliberately:

- **No `1e-5` band, no `1e-8` snap.** Hytale's `Collision1D` needs a skin because its interval test
  is inclusive (`collisionStart > collisionEnd` is the *rejection*, so `start == end` is a hit), which
  makes a resting drone a hit — so it then needs a four-state `kind` classification and a separate
  `touching` flag to rule those back out. The positive-measure rule above gets the same outcome from
  one statement, with no constants to tune. The trade is real: Hytale tolerates up to `1e-5` of
  separation as still-in-contact, and leaves the mover up to `1e-5` short of true contact. Here
  contact is exact and #21 owns any skin it wants.
- **`Contact` is immutable.** Hytale's evaluator *is* its own result object, with mutable fields
  reused per block to avoid allocation — and pays for it: the overlap branch leaves `collisionPoint`
  stale from the previous block, and `Collision1D.kind` is stale after an early-out. Correctness over
  allocation count here; if #21 measures a problem, that is #21's measurement to make.
- **Non-finite input throws rather than degrading.** `CollisionMath.intersect1D` takes the divide
  branch on a NaN direction, and because every NaN comparison is false the axis silently contributes
  no constraint — which can report a hit that is not there. The same shape of bug would make this
  routine return `AlreadyOverlapping` for a NaN displacement, so the displacement is validated.
- **Not `RaycastAABB`'s six-plane form.** It has a live bug worth not reproducing: `nx`, `ny`, `nz`
  are separate accumulators never cleared when a nearer face wins, so it can return an
  unnormalised two-component normal like `(-1, -1, 0)`. It also reports a miss for a zero-length ray
  whose origin is inside the box, where `CollisionMath` reports a hit — the two disagree. This
  routine picks one convention and states it.

### The return type: a sealed interface, three cases

```java
sealed interface SweptResult {
    record Miss()               implements SweptResult {}
    record AlreadyOverlapping() implements SweptResult {}
    record Contact(double entryTime, double exitTime, Vec3 normal) implements SweptResult {}
}
```

Three cases and not two, because **`AlreadyOverlapping` genuinely cannot carry an entry normal.**
The mover did not cross a face; it was already inside. Any normal reported there would be invented.
That is precisely the situation where a sum type beats a nullable field or a boolean flag, and it is
what CLAUDE.md's "prefer values and explicit state machines over booleans-plus-branching" is for.
`Optional<Contact>` was the obvious alternative and was rejected on the same ground: it collapses
"nothing happened" and "you are inside a block" into one `empty()`, and those are opposite problems
for #21.

`Miss` and `AlreadyOverlapping` are empty records exposed as the interface constants
`SweptResult.MISS` and `SweptResult.ALREADY_OVERLAPPING`, so there is one instance of each and
tests can `assertEquals(SweptResult.MISS, result)` — record equality, no identity games.

### `Contact`, field by field

- **`entryTime`** — fraction of the displacement, in `[0, 1)`. The caller gets the impact position
  as `from.plus(displacement.scale(entryTime))`; no helper for that, `Vec3` already reads fine.
- **`exitTime`** — deliberately **not clamped to 1**. It is the time the mover would leave the
  target if the sweep continued, and `exitTime > 1` therefore means *the mover was still inside at
  the end of the tick*. Clamping would throw that away, and it is the one bit both callers want:
  #21 reads it as "ended embedded", #6 as "the pass has not completed yet". Exposed as
  `passedFullyThrough()`. Always finite for a `Contact` — a finite `entryTime` requires at least one
  non-parallel axis, and that axis contributes a finite exit.
- **`normal`** — the **outward** normal of the target face the mover entered through, so it points
  back toward the mover. That is the sign collision response wants, and it is also the sign that
  answers gates.

### How the signed normal answers the gate direction test

A gate has a forward vector `f`: the direction a pilot is required to fly through it. Flying through
correctly means approaching from the `−f` side, which means entering through the face whose outward
normal is `−f`. So:

```
correct direction  ⟺  normal · f < 0
```

That is `Contact.enteredAlong(Vec3 direction)`. A wrong-way pass returns `false` because the normal
is `+f`; a purely sideways clip returns `false` because the dot product is `0` and neither direction
was travelled. #6's "refuses a pass in the wrong direction" is one method call on this result, with
no extra geometry — which is the whole reason for building the routine here rather than twice.

### Where the code lives

```
fpv-core/src/main/java/com/maartenpeels/fpv/math/Aabb.java
fpv-core/src/main/java/com/maartenpeels/fpv/collision/SweptAabb.java
fpv-core/src/main/java/com/maartenpeels/fpv/collision/SweptResult.java
```

`Aabb` sits next to `Vec3` and `Quat` because it is a geometric primitive with no collision
semantics — a set of points. The sweep gets its own `collision` package because it is a routine, and
because #21 and #6 will both import it by name.

`Aabb` is stored as `min`/`max` (that is what a block is) with a `centredAt(centre, halfExtents)`
factory (that is what a drone is), plus `expandedBy`, `translatedBy`, `contains`, `overlaps`,
`centre`, `halfExtents`, `size`. Degenerate boxes — `min == max` on an axis — are **allowed**: a
zero-thickness plane is a reasonable thing to ask about, and the positive-measure rule handles it
without a special case. Inverted boxes (`min > max`) are rejected.

The call site reads:

```java
SweptAabb.sweep(Aabb.centredAt(lastPosition, DRONE_HALF_EXTENTS),
                thisPosition.minus(lastPosition),
                blockBox);
```

`(Aabb, Vec3, Aabb)` rather than a four-argument `(from, to, halfExtents, target)` form
deliberately: three `Vec3` in a row is the positional-transposition hazard `QuadParameters` already
warned about, and the types here make a transposed call not compile.

### What is deliberately *not* here

- **No "sweep against many boxes, return the earliest" helper.** #21 owns candidate-block iteration
  and its own short-circuiting, and #6 tests one gate at a time. Writing the fold now means
  guessing at a signature neither caller has yet asked for.
- **No collision *response*.** No push-out, no reflection, no slide. #21's problem.
- **Nothing touching `QuadIntegrator`.** The integrator stays a pure `(state, input, dt)` function;
  collision is applied around it by #23's tick system, not inside it.

## Test strategy

`ControlInputTest` conventions: `@Nested` per behaviour group, names that state the *reason*.

The five the ticket names, all in `SweptAabbTest`:

- `Miss` — `missesABoxThatIsNowhereNearThePath`, plus a box directly behind the start and one
  beyond the end of the segment (both are misses for different reasons, and both are the kind of
  thing an unclamped slab test gets wrong).
- `FaceHit` — a hit on each of the six faces, asserting the exact `entryTime` and the exact outward
  normal. Six directions, because a sign error on one axis is invisible if you only test one.
- `Tunnelling` — `findsAWallThatANaiveContainmentTestWouldTunnelStraightThrough`: the test asserts
  *both* that the sweep finds it and that overlap-at-`t=0` and overlap-at-`t=1` are both false, so
  the test itself demonstrates the containment check failing. Swept at increasing speed until the
  step is orders of magnitude larger than the wall, to show the answer does not degrade.
- `Glancing` — the tangency family: sliding exactly along a face is a miss; a corner graze where
  `entry == exit` is a miss; a hair inside is a contact. This is the group that keeps #21's "grazing
  a wall does not produce a phantom crash" honest.
- `AlreadyOverlapping` — overlapping at `t = 0`, both moving further in and moving out, and with
  zero displacement.

Plus what flying cannot check:

- `NormalDirection` — the normal always points back toward the mover
  (`normal.dot(displacement) < 0` for every contact in a swept sample), and is a unit axis vector.
- `GateDirection` — `enteredAlong` is true for a correct-direction pass, false reversed, false for a
  sideways clip. Asserted through a **rotated** gate frame as well, so the "transform into the
  gate's local frame" claim above is exercised rather than asserted.
- `passedFullyThrough` true when the sweep clears the box inside the tick, false when it ends
  embedded — checked against a `Contact` whose `exitTime` is greater than 1.
- Determinism and exactness: a head-on hit on an axis lands on an exact `entryTime`, not an
  approximate one, so the assertion is `assertEquals` without a delta.
- Validation: non-finite displacement rejected (the alternative is silent NaN propagation returning
  a bogus `AlreadyOverlapping`, because every comparison against NaN is false); `Contact` rejects an
  out-of-range `entryTime`, a non-increasing `exitTime` and a non-unit normal.
- A zero-extent (point) mover works, because #6 may want a point sweep.
- `SweptResultTest` covers `enteredAlong`, `passedFullyThrough` and the constants.
- `AabbTest` covers `centredAt` round-tripping, `expandedBy`, `overlaps` being strict about
  tangency, degenerate boxes accepted, inverted boxes rejected.

The area is new code, so there is nothing to regress and `/write-tests` is not needed first.

## Risks and judgement calls

Made without asking, because this ran unattended. Each is reversible inside `:fpv-core`.

1. **The drone is a non-rotating world-axis-aligned box.** Slightly generous at extreme attitudes.
   Reversible: a rotating sweep would be a new routine, not a change to this one. It compounds
   slightly in the rotated-gate case, where the drone's world-aligned box is reused unchanged as the
   mover in the gate's frame — which is not its exact silhouette there either. Both approximations
   err generous, and the gate's tolerance is metres while the error is centimetres.
2. **Exact tangency is a miss.** Chosen so a drone resting on the floor does not crash every tick.
   The cost is that a pass that only ever exactly touches a gate does not register — which is the
   right call, since it is also a pass that never entered the gate.
3. **No epsilon anywhere.** If flying reveals phantom crashes from floating-point noise, the fix
   belongs in #21 as a shrunk drone box, not as a constant in here.
4. **`exitTime` is unclamped.** Means `Contact.exitTime` is not a fraction of the segment in the way
   `entryTime` is. Justified above; called out because it is the one asymmetry in the type.
5. **Three-case sealed result instead of `Optional`.** More machinery than the ticket strictly
   demands. Justified by `AlreadyOverlapping` having no honest normal to report.
6. **`Aabb` in `math`, sweep in `collision`.** A judgement about cohesion. If `Aabb` later grows
   collision-specific behaviour it should move.

## Two things the tests caught, worth recording

Both are floating-point traps that a test written after the code would have been written *around*
rather than found.

1. **`Aabb.overlaps` was wrong for degenerate boxes.** The familiar separating-axis form
   `a.min < b.max && b.min < a.max` is equivalent to `max(mins) < min(maxs)` only while both boxes
   are non-degenerate — the familiar form silently drops the `a.min < a.max` and `b.min < b.max`
   terms. So a flat plane lying inside a block was reported as overlapping it, contradicting this
   file's own positive-measure rule. Written as `max(mins) < min(maxs)`, with the reason in the
   javadoc so nobody "simplifies" it back.

2. **A negative displacement produces a `−0.0` entry time.** Dividing an exact `0.0` — which is what
   starting tangent to a face gives — by a negative displacement yields `−0.0`, and `−0.0` compares
   unequal to `0.0` under the IEEE bit equality that records and JUnit both use. So
   `Contact(−0.0, …)` would have been a value that behaved like zero arithmetically and unequal to
   zero in every assertion and every `equals`. Collapsed in `Contact`'s constructor.

The same trap exists one level down, in code this ticket does not own: **`Vec3.negated()` returns
`−0.0` components** for any zero component, so `new Vec3(1, 0, 0).negated()` is not `equals` to
`new Vec3(-1, 0, 0)`. It is arithmetically harmless and equality-hostile, and it is going to bite
whoever consumes these normals in #21 or #6. Left alone here — it is shared math the integrator also
uses and it is outside this ticket — but flagged, and this test file writes its expected normals out
literally rather than deriving them with `negated()` for exactly this reason.
