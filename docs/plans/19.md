# 19 — Attach the pilot camera to the drone in first person, with roll

Part of #4 (phase 0). Depends on #18 (drone entity, `FlightSession`) and #28 (the roll spike).

## The ticket

Attach the pilot's camera to the drone entity in first person, **with roll**, so the horizon tilts
when the quad banks. Detaching on land returns the pilot to a normal view.

## The honest framing: this ticket cannot be verified by a test

The server keeps **no record** of what it told the client the camera should follow.
`CameraManager` (`server/core/entity/entities/player/CameraManager.java:19-24`) holds mouse-button
state, the last screen point and the last targeted block — nothing about attachment. There is no
"get current camera" query, and `SetServerCamera` is fire-and-forget.

So the work splits into three tiers, and the plan is explicit about which tier each claim sits in:

| Tier | What it proves | How |
| --- | --- | --- |
| Unit-testable | The **exact bytes** we put on the wire, field by field, in both modes | `DroneCameraPacketsTest` — pure, no server |
| Harness-testable | We resolve a **real spawned drone**'s network id and attitude, and the session lifecycle fires attach/detach at the right moments | `DroneCameraTest`, `DroneCameraSystemsTest` on `HytaleEcsHarness` |
| Human-only | Whether the **client renders** any of it | `/fpv camera …` instruments + the flight script below |

Runtime bridge between tiers 2 and 3: `/fpv camera status` reads
`playerRef.getPacketHandler().getPacketStatsRecorder().getEntry(280).getSentCount()`
(`protocol/io/PacketStatsRecorder.java`, recorder created unconditionally per connection at
`server/core/io/netty/HytaleChannelInitializer.java:93-94`). That distinguishes "we never sent it"
from "we sent it and the client ignored it" — the single most expensive ambiguity to debug by eye.

## What #28 actually concluded (and a correction to the brief for this ticket)

#28 has four comments. The **second** says `AttachedToPlusOffset` "was never exercised". The
**fourth explicitly supersedes that**: it ran with the correct named-argument form
(`/fpv rolltest --degrees 30 --offset true`) and **both modes render roll.**

The fourth comment also reverses the design conclusion, and its reasoning is sound:

> For a **server-simulated** drone the sim owns all three angles. Every tick we push the drone's
> full attitude, so having the client stop applying its own mouse-driven yaw/pitch to the camera is
> **correct, not a limitation**. […] `Custom` with the drone's complete yaw/pitch/roll is the clean
> path.

plus an observed behavioural detail against offset mode: with a roll offset applied, mouse
left/right **yaws about the world axis, not the rolled camera's own up-axis** — which is not how a
rolled aircraft behaves.

**Judgment call: ship both modes, config-selectable, and do not pick a winner in code.** Reasons:

1. The two modes fail for *independent* reasons, and neither can be ruled out from the sources.
2. `AttachedToType.EntityId` is **completely unexercised** — see the risk section. Offset mode
   depends on it entirely; `Custom` mode does not depend on it at all.
3. #24's verdict on whether 30 TPS feels flyable depends on the lerp/smoothing behaviour, which
   differs between a one-shot attach and a per-tick push. Knowing which one feels connected is
   worth more than saving one enum.

Still unresolved by #28 and owned here: the spike attached to the **local player**. Roll alongside
`attachedToType = EntityId` + `skipCharacterPhysics` on a real drone entity is new ground.

## Verified facts this design rests on

Read out of `~/.gradle/caches/hytale-decompiled/release-0.5.9/server/com/hypixel/hytale/`.

### The packet

- `SetServerCamera` — `PACKET_ID = 280`, `ToClientPacket`, `MAX_SIZE = 157`, channel `Default`
  (`protocol/packets/camera/SetServerCamera.java:17-29`). Constructor
  `(ClientCameraView, boolean isLocked, @Nullable ServerCameraSettings)`. No builder; fields public.
- `ClientCameraView` = `FirstPerson(0)`, `ThirdPerson(1)`, `Custom(2)`. **Every one of the five
  in-tree senders uses `Custom`**; `FirstPerson`/`ThirdPerson` are never sent.
- **Detach is `new SetServerCamera(ClientCameraView.Custom, false, null)`** — not a `FirstPerson`
  view, not a separate packet. Identical at `PlayerCameraResetCommand.java:33` and
  `CameraManager.java:40`.
- Send idiom: `playerRef.getPacketHandler().writeNoCache(packet)`. `writeNoCache` because the
  payload is per-player and unique; `write` wraps in a shared `CachedPacket`
  (`server/core/io/PacketHandler.java:217-255`).

### `ServerCameraSettings` defaults that matter

`protocol/ServerCameraSettings.java:20-67`. Three defaults are traps:

- **`allowPitchControls` defaults to `false`.** #17 (`docs/plans/17.md:109`) requires `true` or its
  pitch channel goes dead. **We must set it explicitly.**
- `applyLookType` defaults to `LocalPlayerLookOrientation`, which is what #17 needs
  (`docs/plans/17.md:106-108`). We leave it alone and never write `ApplyLookType.Rotation`.
- `rotationType` and `positionType` **both default to `AttachedToPlusOffset`**, and
  `attachedToType` defaults to `LocalPlayer`. So a bare `new ServerCameraSettings()` is already
  "offset mode attached to yourself" — silence is a choice here, which is why
  `DroneCameraPackets` sets every field it depends on explicitly.

Also: `movementForceRotationType` defaults to `AttachedToHead`, which is the frame #17's one-arg
`ClientMovementAdapter.sample(packet)` assumes. **We deliberately do not touch it**, so #17's
adapter keeps working unchanged.

### Roll reaches the client for a non-player entity — confirmed on the wire

This is what makes the tracked mode conceivable at all:

`TransformComponent.rotation` is a `Rotation3f` (`math/vector/Rotation3f.java:33-35`:
`x`=pitch, `y`=yaw, **`z`=roll**) →
`PositionUtil.assign(Direction, Rotation3fc)` copies **all three**, roll included
(`server/core/util/PositionUtil.java:58-62`) →
`ModelTransform.bodyOrientation` / `.lookOrientation` →
`TransformUpdate` (`ComponentUpdateType.Transform = 9`) → `EntityUpdate` →
`EntityUpdates` **packet 161**.

Built by `TransformSystems.EntityTrackerUpdate.tick`
(`server/core/modules/entity/system/TransformSystems.java:61-93`), whose query is
`Query.and(Visible, TransformComponent)` — **no player requirement**, so a drone goes through it.
`bodyOrientation` comes from `TransformComponent`, `lookOrientation` from `HeadRotation`. Roll is
unclamped on this path; nothing in the tree zeroes it.

Two consequences worth writing down:

- The update is **change-gated** (`TransformSystems.java:80-82`) — re-writing the same rotation
  sends nothing. Good for us.
- `NetworkId` must be set or `EntityTrackerSystems` throws
  `IllegalArgumentException("Invalid entity network id")` (`EntityTrackerSystems.java:1046-1051`).
  #18's `EnsureDroneNetworkSendable` already guarantees it.

**`ModelTransform` via `EntityUpdates` is the only server→client channel for a live entity's
3-axis orientation.** There is no alternative packet — `MountMovement` and `ClientMovement` are
client→server, `MountedUpdate` carries an offset with no rotation.

### `NetworkId`, not `Ref.getIndex()`

`attachedToEntityId` is an `int` (`ServerCameraSettings.java:38`, `writeIntLE` at `:635`). The id is
the **network** id: `store.getComponent(ref, NetworkId.getComponentType()).getId()`
(`server/core/modules/entity/tracker/NetworkId.java`), the same thing `AnimationUtils.java:52-54`
and `InteractionContext.java:342-344` use. `Ref.getIndex()` is an ECS slot and is **not** the wire
id.

### `Direction` is radians, and its constructor order is `(yaw, pitch, roll)`

`protocol/Direction.java:17-24`. `PlayerCameraTopdownCommand.java:50` passes `-Math.PI / 2` to look
straight down. `Rotation3f`'s order is `(pitch, yaw, roll)`. **The two are transposed on the first
two arguments** — the single likeliest bug in this change, so `DroneCameraPackets` has one
conversion point and a test that would fail if yaw and pitch were swapped.

### No sign flip belongs in this ticket

CLAUDE.md is right that Hytale's `Direction.pitch` is positive nose-**up**, opposite to
`ControlInput.pitch`. But this ticket reads `TransformComponent.getRotation()`, which is *already*
Hytale-native — it is the same value `PositionUtil.assign` feeds straight into a `Direction` with no
negation. **The `ControlInput` → Hytale negation belongs where the sim writes attitude into
`TransformComponent`, which is #24.** Doing it here as well would double-negate and roll the
horizon the wrong way. Recorded because the temptation is strong and the bug is invisible.

### Camera state is sticky, and world transfer clears it

- **No system in the tree re-sends `SetServerCamera`.** Five one-shot call sites, none ticking.
- **A world change resets the camera**: `Universe.java:1239` → `Player.resetManagers`
  (`server/core/entity/entities/Player.java:348-356`) → `CameraManager.resetCamera`, which also
  clears `EntityTrackerSystems` state (so a tracked network id is stale afterwards).
  We need no special handling: #18's `EndSessionOnPilotRemoved` ends the session on the same
  transition, so there is no session left to hold a camera.
- No camera reset on respawn or death; a reconnect is a fresh client with no session.
- `PlayerCameraAddSystem` only `ensureComponent(CameraManager)` and sends nothing.

### The lifecycle hook: `RefChangeSystem`, not `RefSystem`

This was the one mechanism I had wrong going in. **`RefSystem.onEntityAdded` does not fire when a
component is added to a live entity.** It is invoked from exactly four places, all entity-lifecycle
(`Store.addEntity`/`addEntities`/`removeEntity`/`removeEntities`).

Component transitions dispatch to **`RefChangeSystem<ECS_TYPE, T>`**
(`component/system/RefChangeSystem.java:11-22`) with `onComponentAdded` / `onComponentSet` /
`onComponentRemoved`. Dispatch sites: `Store.datachunk_addComponent` at `Store.java:2052-2057`,
`Store.putComponent` (existing-component branch) at `:951-964`, `Store.removeComponent` at
`:1054`, `removeComponentIfExists` at `:1105`.

Three conditions must all hold (`Store.java:2052-2057`): the system extends `RefChangeSystem`,
`componentType().getIndex()` matches exactly, and `getQuery()` matches the **post-transition**
archetype.

That is exactly the hook this ticket wants: `FlightSession` appearing on a pilot means "attach",
disappearing means "detach". It keeps camera code out of `FlightSessions`, which preserves plan
18's deliberate scope boundary against #22 (`docs/plans/18.md:249-256`).

Two gotchas designed around:
- A second `putComponent` of an existing session yields `onComponentSet`, **not**
  `onComponentAdded`. We implement both so re-pointing a session re-attaches.
- `tryRemoveComponent` on an entity that lacks the component is completely silent — which is why
  both teardown routes in #18 (`FlightSessions.land` and `ClearSessionOnDroneRemoved`) stay
  idempotent through this system too.

## The two modes

### `TRACKED` — `RotationType.AttachedToPlusOffset`

```
attachedToType     = EntityId
attachedToEntityId = drone's NetworkId
positionType       = AttachedToPlusOffset
positionOffset     = Position(0, eyeHeight, 0)
rotationType       = AttachedToPlusOffset
rotationOffset     = Direction(0, cameraUptilt, 0)
```

One packet per session. The client tracks the drone's position and rotation itself, and roll rides
along inside `bodyOrientation` (proven on the wire above). Cheapest, and the mode the ticket brief
names. Entirely dependent on `AttachedToType.EntityId`.

### `DRIVEN` — `RotationType.Custom`

```
attachedToType = None
positionType   = Custom      position = drone position + (0, eyeHeight, 0)
rotationType   = Custom      rotation = Direction(yaw, pitch + uptilt, roll)
```

Re-sent every tick by `DroneCameraSystems.PushDrivenCamera`. Uses **only** the path #28 proved
renders roll, and touches neither `EntityId` nor offset semantics. Costs 157 B × 30 Hz ≈ 4.7 kB/s
per pilot — ~38 kB/s at the 8-pilot target of decision 9, which is acceptable next to chunk
streaming.

This is the fallback that stops an unexercised enum value from blocking phase 0.

## Fields set the same way in both modes, and why

| Field | Value | Reason |
| --- | --- | --- |
| `isFirstPerson` | `true` | the ticket: FPV, not a chase cam |
| `skipCharacterPhysics` | `true` | decision 4; stops the parked body's physics interfering |
| `allowPitchControls` | `true` | **not the default** — #17 dies without it |
| `applyLookType` | untouched (`LocalPlayerLookOrientation`) | #17 reads that channel |
| `movementForceRotationType` | untouched (`AttachedToHead`) | the frame #17's one-arg `sample` assumes |
| `eyeOffset` | `false`, explicitly | client-side meaning, never read server-side, but every in-tree sender writes `true` and the circumstantial evidence (`Model.java:178`, `TargetUtil.java:388-398`) is that it silently adds the model's `EyeHeight` to camera Y. We supply our own offset; two offsets would double up |
| `displayReticle` | `false` | a drone feed has no crosshair |
| `displayCursor` | `false` (default) | not a cursor UI |
| `sendMouseMotion` | `false` (default) | the `MouseInteraction`/packet-111 channel #17 recorded as a fallback, not used yet |
| `canMoveType` | untouched (`AttachedToLocalPlayer`) | semantics unknown, no in-tree precedent for changing it |
| `isLocked` | `true`, **config-overridable** | all three in-tree camera commands lock. But locking might also be what kills look input, and #17 needs look input alive — so this is the first knob to flip if the sticks go dead |

`positionLerpSpeed` / `rotationLerpSpeed` default to `1.0` in the protocol; the in-tree camera
commands all use `0.2`. Both are **config values plus a runtime command**, per the ticket's note
that they may be the difference between floaty and connected at 30 TPS.

## Risks, stated plainly

1. **`AttachedToType.EntityId` has zero usages in the entire decompiled tree** — outside
   `ServerCameraSettings` itself, nothing sets `attachedToType` or `attachedToEntityId`. All five
   in-tree senders leave it at `LocalPlayer`. And there is **no client tree in the cache**
   (`release-0.5.9/` contains only `server/`), so the client's interpretation is unreadable. It is a
   valid wire value that may be unimplemented. This is the single largest unknown in the ticket, and
   the whole reason `DRIVEN` exists.
2. **`positionOffset` / `rotationOffset` frames are undocumented** — never set anywhere in the tree.
   Body-frame vs world-frame is observable (a body-frame vertical offset swings out as the drone
   rolls; a world-frame one does not) and the flight script asks the human to look.
3. **`isLocked` may kill look input**, breaking #17. Mitigated by making it a runtime knob.
4. **`HideParkedBody` interaction** — the parked body is pruned from every viewer's `visible` set.
   The drone is a separate entity and is not pruned, so attaching to it is unaffected. Worth
   knowing that a `TRACKED` camera attached to a *pruned* entity would be a different story.

### The `PilotSink` seam, and why `FlightComponentTypes` was left alone

The obvious way to reach a pilot's connection is `PlayerRef.getPacketHandler()`, adding
`PlayerRef` to `FlightComponentTypes` like every other component type. That was the first
version, and it was wrong twice over:

- **It made the whole feature untestable.** `PlayerRef` cannot be built in a harness — its
  constructor needs a `PacketHandler` and a `ChunkTracker`, i.e. a live connection — and
  `PlayerRef.getComponentType()` additionally needs a booted `Universe`. With the lookup inlined
  into `DroneCamera`, nothing past "we decided to send" could be asserted.
- **It would have collided with #23**, which touches the same record.

One functional interface fixes both. `PlayerRefSink` is the only line a harness cannot run, and
`FlightComponentTypes` is untouched, so the #23 rebase stays mechanical. For the same reason
`PushDrivenCamera`'s query is just `flightSession()` and not `Query.and(flightSession, playerRef)`:
the extra term filters out nothing real — only pilots have sessions — while putting the system out
of the harness's reach.

## Why the diagnostic commands are part of this ticket, not gold-plating

#22 owns `/fpv launch` and `/fpv land` and does not exist yet. Without a way to start a session and
without a flight model (#24) to bank the drone, **there is no way for a human to verify this ticket
at all** — and a human is the only thing that can verify it. So this ticket ships its own
instrument:

- `/fpv camera on` / `off` — start and end a diagnostic session (delegates to `FlightSessions`)
- `/fpv camera attitude --roll 30` — write attitude straight into the drone's `TransformComponent`
  and `HeadRotation`, in degrees, converted to radians once. This is what makes the horizon tilt
  with no physics at all, and it is the exact gap #28 left: roll on a **real attached drone
  entity**.
- `/fpv camera set --view driven --rotlerp 0.2` — bisect the two modes and the smoothing without a
  rebuild
- `/fpv camera status` — mode, tuning, drone network id, and the packet-280 sent count

`#22` should absorb or delete `on`/`off`; the rest are keepers for as long as the camera is
suspect. Collision surface with #22 is one `addSubCommand` line in `FpvCommand`.

## Flight-test script

**This is the deliverable that settles the ticket.** Everything above is scaffolding for it.

Launch the server **from this worktree** — a stale jar was the single most expensive trap in #28,
and the tell is subtle: a genuinely missing subcommand fails with *"subcommand not found"* plus
fuzzy suggestions, whereas an argument-count error means the parser found a `/fpv` with zero
subcommands, i.e. old classes. Three places a stale build hides:
`fpv-plugin/build/classes/java/main/`, `fpv-plugin/build/libs/*.jar`, `server/mods/*-dev.jar`.

```bash
cd .worktrees/19
JAVA_HOME=$(/usr/libexec/java_home -v 25) ./gradlew runServer
```

**Remember optional args are named.** `--roll 30`, never a bare `30`.

### Step 0 — baseline

```
/fpv camera status
```

Expect `view=TRACKED rotationType=AttachedToPlusOffset locked=true posLerp=0.200 rotLerp=0.200`
and `sent to you: 0`.

### Step 1 — attach, and confirm the packet left the building

```
/fpv camera on
/fpv camera status
```

`on` reports a `networkId`. `status` must now show `flying=true`, the same `droneNetworkId`, and
**`sent to you: 1`**.

- **`sent` still 0** → our bug, not the client's. Stop; nothing below will mean anything.
- **`networkId=?`** → the drone spawned without a `NetworkId`; #18's `EnsureDroneNetworkSendable`
  is broken.

You should now be looking out of the drone, unable to see your own body.

### Step 2 — the question the ticket exists to answer, in `TRACKED`

```
/fpv camera attitude --roll 0
/fpv camera attitude --roll 15
/fpv camera attitude --roll 30
/fpv camera attitude --roll 90
/fpv camera attitude --roll 180
```

Each prints the degrees **and** the radians it converted to. Sanity-check the radians: 30° must
read `0.5236`. If a command ever echoes a radian value equal to the degrees you typed, the
conversion has been lost and everything after is meaningless — that is the mistake that nearly
killed #28.

**Look for:** the horizon rotating progressively. 15° slight, 30° obvious, 90° fully sideways,
180° inverted.

**Failure shapes, and what each means:**

| What you see | What it means |
| --- | --- |
| Horizon tilts progressively | `AttachedToPlusOffset` composes roll onto a tracked entity. Best case — the ticket is done as designed. |
| **View never moves at all, at any angle** | The camera is not following the drone. Most likely `AttachedToType.EntityId` is unimplemented client-side — it has zero usages in the whole decompiled server. **Go to step 3; this is the specific thing #28 could not test.** |
| Position follows the drone but roll is ignored | Attachment works, offset rotation does not. Try `--uptilt 30` — if pitch is ignored too, `rotationOffset` is being dropped wholesale rather than roll specifically. |
| Snaps between a few angles | Roll is quantised. Record the step size. |
| Tilts but stops beyond some angle | Roll is clamped. Record the limit. |
| Garbage / wild spinning | A unit bug on our side. Re-read the echoed radians. |

### Step 3 — the fallback, in `DRIVEN`

```
/fpv camera set --view driven
/fpv camera attitude --roll 30
/fpv camera attitude --roll 90
```

`DRIVEN` uses `RotationType.Custom`, the mode #28 **did** confirm renders roll, and it never
mentions `attachedToEntityId`. So this is the discriminator:

- **Tilts in `DRIVEN`, ignored in `TRACKED`** → `AttachedToType.EntityId` and/or offset rotation is
  unusable. **This is a real finding, not a pass — say so loudly.** Phase 0 is unblocked (switch
  the config default to `driven` and accept ~4.7 kB/s per pilot), but `TRACKED` should be recorded
  as dead and #28's optimistic fourth comment corrected.
- **Neither mode tilts** → contradicts #28 outright. Suspect the drone entity, not the camera:
  check `status` shows `flying=true`, then whether `/fpv camera off` restores a normal view (if
  even that fails, packets are not reaching this client at all).
- **Both tilt** → best outcome. Keep `TRACKED` as the default; it costs no per-tick bandwidth.

In `DRIVEN`, also check the view **tracks the drone as it moves** — that mode re-sends an absolute
position every tick, so a frozen camera means `PushDrivenCamera` is not running.

### Step 4 — smoothing. #24's verdict depends on this

Whichever mode works, try each of these and note how the camera *feels*, not just whether it works:

```
/fpv camera set --poslerp 1.0  --rotlerp 1.0     # no smoothing: rawest, most connected, may jitter
/fpv camera set --poslerp 0.2  --rotlerp 0.2     # Hytale's own camera commands use this
/fpv camera set --poslerp 0.5  --rotlerp 1.0     # smooth position, instant rotation
/fpv camera set --poslerp 0.1  --rotlerp 0.1     # heavy: should feel floaty and laggy
```

`1.0` is the protocol default; `0.2` is what all three in-tree camera commands use. **Rotation is
the one that matters** — roll is the fastest-changing angle on a quad. Record which felt
connected. If nothing feels connected even at `1.0`, the problem is the 30 Hz tick, not smoothing,
and that is decision 3's escape hatch (`/world tps 120`) rather than a camera fix.

### Step 5 — does the look channel still work?

`isLocked = true` is the in-tree precedent but is the likeliest thing to kill the input channel
#17 reads, and dead sticks do not look like a camera bug.

```
/fpv camera set --locked false
```

Move the mouse. If look input was dead before this and alive after, **`isLocked` must default to
`false`** — change `CameraLocked` in the config and note it on the ticket.

### Step 6 — the Done-when

```
/fpv camera off
```

Normal view, own body visible, mouse look normal. Then `/fpv camera status` → `flying=false`.

Run `on`/`off` three times in a row: no drift, no stuck camera, no doubled drones.

### What to write on the ticket

1. Which modes tilted the horizon — `TRACKED`, `DRIVEN`, both, neither.
2. Whether roll was continuous, quantised or clamped.
3. The lerp values that felt best, and whether smoothing helped at all.
4. What `isLocked` did to look input.
5. Whether `off` reliably restored a normal view.
