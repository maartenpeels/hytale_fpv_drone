# Plan — #17 Adapt `ClientMovement` into `ControlInput` at the packet boundary

Ticket: [#17](https://github.com/maartenpeels/hytale_fpv_drone/issues/17) · Epic: #4 · Milestone: v0.1 — Feel

Branch base: `feat/34-plugin-test-harness` (PR #37, unmerged at the time of writing — this change
wants the `:fpv-plugin` test source set that #34 wires up).

## What the ticket asks for

Read `ClientMovement` (packet 108) and produce a `ControlInput`. Nothing downstream sees a packet
(decision 1). Garbage input clamps instead of throwing. The axis mapping is written down where the
next person finds it, with a documented sign convention.

Two things were handed to this ticket as already decided:

1. **Throttle rides the forward axis of `wishMovement`, remapped bipolar:** `throttle = (forward + 1) / 2`.
   Yaw rides the lateral axis. Pitch and roll come from `lookOrientation`.
2. **The mapping math lives in `:fpv-core`** as a pure function over plain numbers; the plugin side is
   a shell that unpacks packet fields and calls it.

The open question this ticket has to settle is whether pitch/roll stick deflection comes from
`lookOrientation`'s **per-tick delta** or from its **absolute angle**. That is answered below.

## What the decompiled server actually says

Everything in this section was read out of
`~/.gradle/caches/hytale-decompiled/release-0.5.9/server/`. Four of these findings were **not** in
CLAUDE.md and two of them contradict assumptions the ticket was written on, so they are recorded
here in full.

### `ClientMovement` and where its fields go

`protocol/packets/packets/player/ClientMovement.java` — every field is `@Nullable` and public.
`server/core/io/handlers/game/GamePacketHandler.java:274-360` is the only handler. It:

- disconnects on a non-finite `absolutePosition`, `bodyOrientation` or `lookOrientation`
  (`ValidateUtil.isSafeDirection` checks **finiteness only** — there is no range check, so yaw and
  pitch are any finite float);
- does **not** validate `wishMovement` at all;
- translates each present field into a `PlayerInput.InputUpdate` queued on the player's
  `PlayerInput` component: `SetHead(lookOrientation)`, `WishMovement(x, y, z)`, and so on.

### `Direction` is in **radians**

Not stated in CLAUDE.md, and it decides whether the mapper's constants are degrees or radians.

- `math/vector/Vector3dUtil.setYawPitch(double yaw, double pitch, …)` calls
  `TrigMathUtil.cos(pitch)` / `TrigMathUtil.sin(yaw)`, and
  `math/util/TrigMathUtil.java:14-28` declares those parameters `radians`.
- `math/rotation/Rotation3f.addRotationOnAxis(Axis, int degrees)` converts:
  `float rad = (float)(Math.PI / 180.0) * degrees` — i.e. the stored representation is radians and
  degrees are the thing needing conversion.

`PlayerInput.SetHead` writes straight into `HeadRotation.getRotation()`, a `Rotation3f`. So
`Direction.yaw/pitch/roll` are radians end to end. `:fpv-core` already works in rad/s
(`BodyRates`), so **no unit conversion happens at this boundary** — which is worth knowing, because
a silent degree/radian mix-up here is a 57× sensitivity error that would read as "the mouse is
broken".

### `wishMovement` is a **world-space** vector, not a body-local stick vector

This one contradicts the ticket's premise that `wishMovement` has a "forward component" and a
"lateral component" you can read straight off `z` and `x`. Three independent pieces of evidence:

1. `ServerCameraSettings` (`protocol/ServerCameraSettings.java:32-34`) carries
   `MovementForceRotationType movementForceRotationType` (`AttachedToHead` / `CameraRotation` /
   `Custom`) plus a nullable `Direction movementForceRotation`. That setting only makes sense if the
   **client** rotates the raw stick vector by some rotation before sending it. The default is
   `AttachedToHead`.
2. `KnockbackPredictionSystems.java:95-97` does
   `relativeMovement.set(wish.getX(), wish.getY(), wish.getZ())`, and at `:115-119` the fallback
   when no `WishMovement` arrived is `relativeMovement.set(client).sub(clientLast)` — a **world-space
   position delta**. The two are interchangeable in that code, so `wishMovement` is in world axes.
3. It is then consumed as `velocity.fma(converter, rel)` (`:402-403`), i.e. added to a world-space
   velocity.

So the adapter has to **un-rotate** `wishMovement` by the frame yaw to recover forward/lateral. That
is a two-line planar rotation, but getting it wrong produces the classic "controls are inverted when
I fly north" bug, which is exactly the kind of thing decision 10 wants under core unit tests.

Its **magnitude is unverifiable from server sources.** Quake's `wishdir` (which the name and the
`fma` usage both echo) is a unit direction times a speed scalar, so the magnitude may well not be
`1.0` at full deflection. This is handled by making full-scale a config value, defaulted to `1.0`,
that #24 can correct by flying — see "Unknowns" below.

### `wishMovement` is not stored anywhere — `PlayerInput.WishMovement.apply` is a no-op

`PlayerInput.java:288-290`. Unlike `SetHead` (which lands in `HeadRotation`) and `SetBody` (which
lands in `TransformComponent`), the wish vector is queued and then dropped; only
`KnockbackPredictionSystems` and `MountSystems` ever read it, and
`PlayerSystems.ApplyPlayerInput` (`:663-669`) clears the queue every tick.

**Consequence for #24, not for this ticket:** there is no component to read the wish vector out of
after the fact. Whoever wires this adapter into a live tick has to either read
`PlayerInput.getMovementUpdateQueue()` **before** `ApplyPlayerInput` clears it, or intercept packet
108. And `server/core/plugin/JavaPlugin.java` is 34 lines with no packet-handler API at all
(`getFile`, `getClassLoader`, `getType`), so there is no supported plugin hook for packet 108 —
the queue is the realistic route. Flagged loudly here because it is a genuine risk to #24 and it is
cheaper to know now.

### Two camera settings the input channel depends on

Both matter to #18/#28 and are recorded because this adapter silently stops working if they are set
wrong:

- `ApplyLookType` is `LocalPlayerLookOrientation` (default) or `Rotation`. Only the default keeps
  mouse/right-stick motion flowing into the player's own look orientation, which is the channel this
  adapter reads. Set `Rotation` and pitch/roll go dead.
- `allowPitchControls` must stay `true` or the pitch channel goes dead.

### A separate relative-motion channel exists (noted, not used)

`ServerCameraSettings.sendMouseMotion`, when true, makes the client attach a
`MouseMotionEvent { MouseButtonType[] mouseButtonType, Vector2i relativeMotion }` to
`MouseInteraction` (packet **111**), surfaced server-side as `PlayerMouseMotionEvent` — a real
plugin event, unlike packet 108. `relativeMotion` is **raw relative pixels**, which is a cleaner
pitch/roll source than differencing an absolute angle, and it comes with an event hook.

Not used here: it is a different packet (out of this ticket's scope), it is `Vector2i` pixels with
no known scale, and it presumably only fires for mouse input, not a gamepad right stick — so it
would solve one input device and not the other. Recorded as the fallback if delta-of-look turns out
too coarse in #24.

### A correction to CLAUDE.md's axis note

CLAUDE.md says of `Vector3dUtil.setYawPitch`: *"yaw increases toward −X, i.e. **opposite** to a
right-handed yaw about +Y."* The first half is right and the second half is wrong.

The standard right-handed rotation about `+Y` is
`Ry(θ)·v = (v.x·cosθ + v.z·sinθ, v.y, −v.x·sinθ + v.z·cosθ)`. Applied to Hytale's forward axis
`(0, 0, −1)` that gives `(−sinθ, 0, −cosθ)` — which is *exactly*
`setYawPitch`'s `x = −sin(yaw)·cos(pitch)`, `z = −cos(yaw)·cos(pitch)`. So Hytale's yaw **is** a
right-handed rotation about `+Y`, not its opposite.

The *conclusion* CLAUDE.md draws survives, for a different reason: `Vector3dUtil` also fixes
`RIGHT = (1, 0, 0)` and `FORWARD = NORTH = (0, 0, −1)`, and `forward × up = +X`, so `+X` is the
aircraft's right. Increasing yaw takes forward `−Z` toward `−X`, which is the aircraft's **left**.
`ControlInput.yaw` is transmitter convention, positive nose-**right**. So a look-yaw *angle* still
has to be negated on the way to `ControlInput.yaw`/`roll` — just because increasing yaw turns left,
not because the rotation is left-handed.

Worth separating, because the two statements imply different code for the wish-vector un-rotation:
under the (wrong) left-handed reading the rotation matrix would need its sine terms flipped, and the
result would be "strafe right yaws left", i.e. a bug nobody could point at.

Not edited into CLAUDE.md — two open PRs already touch that file, and the "Settled decisions" /
verified-facts sections are ask-first. Reported instead.

## The open decision: absolute angle or per-tick delta

**Decision: per-tick delta, on both axes.** `roll` from Δ`lookOrientation.yaw`, `pitch` from
Δ`lookOrientation.pitch`, each divided by `dt` to get an angular rate and then normalised against a
configurable full-scale look rate.

### Why roll leaves no choice

`ControlInput` needs a roll axis; a quad without one cannot fly. `Direction` has a `roll` field, but
nothing a pilot can touch produces camera roll — a mouse and a gamepad right stick both drive yaw
and pitch, and nothing else. `lookOrientation.roll` is therefore dead, in both input modes, and roll
has to come from the look **yaw** channel.

Look yaw is absolute, unbounded and wrapping (`isSafeDirection` only rejects non-finite, so it is
any finite float and accumulates as the pilot spins). An absolute mapping of yaw onto a roll stick
would mean "how much you are rolled depends on which compass direction you face", which is not a
control at all. So roll is a delta, necessarily. That leaves pitch: match it, or ship two axes on
one physical stick with opposite behaviours.

### Why delta beats absolute on pitch too

Absolute pitch is *available* — bounded to roughly ±90°, no wrap, self-holding, identical on mouse
and gamepad. It loses anyway, for three reasons:

1. **Rate mode wants a self-centring stick, and a delta *is* a self-centring stick.** Downstream,
   `ControlInput.pitch` is a stick *position* that #15's rate curve turns into a demanded angular
   *rate*. Holding half stick means "keep rotating", not "sit at 45°". The physical stick this
   models springs back to centre when released — and "the pilot stopped moving the mouse" maps onto
   "the stick returned to centre" exactly. Absolute angle is angle-mode-shaped, and there is no
   angle mode in this project.
2. **The pilot cannot see their own head.** Decision 4 attaches the camera to the *drone*, so the
   view shows the drone's attitude and the player's own look orientation is invisible. An absolute
   axis with no on-screen indicator is a stick whose position the pilot cannot know: you would be
   holding an unknown amount of pitch, with the available headroom depending on invisible history
   (how close you already are to the ±90° stop). Under delta, "I am not moving the mouse" is
   self-evidently "the stick is centred" — the feedback is in your hand.
3. **Delta is the one rule that fits both input devices, which is the whole point of decision 1.**
   A mouse produces unbounded relative motion: absolute yaw is meaningless for it, and delta is its
   native quantity. A gamepad right stick self-centres, and the client converts its deflection into
   a look *rate* — so holding the stick right yields a constant Δyaw per tick, i.e. a constant roll
   deflection. Both devices land on the same mapping. That is what lets decision 1's bet — "only
   this adapter changes when gamepads land" — actually come true; controllers shipped in Update 5
   (2026-05-26) and are still unverified on hardware here, so a mapping that only works for one
   device would be a coin flip.

### What delta costs, and how each cost is paid

Honest accounting, because this is the choice #24's verdict hangs on:

| Cost | Mitigation |
| --- | --- |
| Δ per tick scales with tick length, so raising TPS would silently multiply sensitivity | Divide by `dt` to get rad/s before normalising. Decision 3's escape hatch (`setTps(120..240)`) stays a config change. |
| Yaw wraps: 359° → 1° reads as a −358° flick | Wrap the delta into `(−π, π]` with `Math.IEEEremainder`. |
| A sustained input is impossible — mouse travel runs out, and at the ±90° pitch stop the client stops producing Δpitch | Accepted. In rate mode a pitch input *is* transient: flick to set attitude, centre, the drone holds it. This is the shape acro flying already has. If #24 disagrees, packet 111's `relativeMotion` is the escape hatch. |
| A stalled or silent client produces zero delta | That is the correct failure mode: sticks centre. `PilotInputMapper.centred` makes it explicit, and rests throttle at mid-stick rather than cutting motors. |
| Client frame rate ≠ tick rate, so a low-FPS client gets chunkier input | Accepted and documented. Accumulating deltas within a tick and dividing by the tick's `dt` means a high-FPS client gets no advantage, only smoother resolution. |
| Full-scale look rate is a guess | It is a config value (`PilotInputMapping`), defaulted to 2π rad/s (360°/s — one full turn per second at full stick), to be corrected in #24. This is also where decision 11's calibration wizard will eventually plug in. |

## Design

### Split

Everything with arithmetic in it is in `:fpv-core`. The plugin class copies packet fields into a
record and performs **no** arithmetic at all — not even the sign flips, which are core's job because
they are the part most worth testing.

```
fpv-core/…/fpv/control/
  PilotInputSample.java     raw, untrusted, per-packet snapshot in world convention
  LookTrack.java            the previous absolute look — the delta's memory
  PilotInputMapping.java    full-scale constants (the "gains" of this mapper)
  PilotInputMapper.java     the pure function: (mapping) × (track, sample, dt) → update
  PilotInputUpdate.java     (ControlInput, LookTrack) — result plus next state

fpv-plugin/…/fpv/plugin/input/
  ClientMovementAdapter.java   ClientMovement → PilotInputSample. Field copies and null checks.
```

State handling follows the established `RatePid` / `RatePidState` / `RatePidUpdate` shape: an
immutable state record in, a `(result, nextState)` record out, one stateless mapper instance shared
by every pilot flying the same sensitivities.

### Conventions at the seam

`PilotInputSample` is documented as being in the world convention `:fpv-core` and Hytale already
share, so the plugin never converts: `+Y` up, forward `−Z`, right `+X`, yaw a right-handed rotation
about `+Y` (so **increasing yaw turns the nose left**), pitch positive nose-**up**, angles in
**radians**.

`NaN` is a meaningful value in the sample, not an error: it means "this packet did not carry that
field". `lookOrientation` is `@Nullable` and the client omits it when the look has not changed, so
that case is common rather than exceptional.

### The mapping

With `θ` the wish frame yaw, `wx`/`wz` the wish vector's horizontal components:

```
forward  = −(sin θ · wx + cos θ · wz) / wishFullScale        un-rotate by −θ, then read −Z
lateral  =  (cos θ · wx − sin θ · wz) / wishFullScale        …and +X

throttle = (forward + 1) / 2
yaw      =  lateral
roll     = −(Δlook.yaw   / dt) / rollLookRateFullScale
pitch    = −(Δlook.pitch / dt) / pitchLookRateFullScale
```

then `ControlInput.clamped(throttle, roll, pitch, yaw)`.

Sign notes, since these are the two-out-of-three CLAUDE.md warns about:

- **`yaw = +lateral`, not negated.** The negation rule applies to Hytale *angles*, not to spatial
  axes. `+X` is the aircraft's right, and strafe-right maps to yaw-right, which is positive
  `ControlInput.yaw`. Negating here would be a wrong application of a right rule.
- **`roll = −Δyaw`.** Increasing Hytale yaw turns the nose left (see the correction above); moving
  the mouse right decreases yaw; transmitter-positive roll banks right. So mouse-right → −Δyaw > 0 →
  bank right.
- **`pitch = −Δpitch`.** Hytale pitch is positive nose-up; `ControlInput.pitch` is positive
  nose-down.

Why this is Mode 2, which is the reason the throttle decision holds: `wishMovement` is the left
stick (WASD / left stick) and gives throttle on its vertical and yaw on its horizontal;
`lookOrientation` is the right stick (mouse / right stick) and gives pitch on its vertical and roll
on its horizontal. That is a Mode 2 transmitter, axis for axis. The bipolar throttle remap is what a
*spring-centred* stick requires — centre is mid-throttle, not motors-off — and it degrades correctly
onto a keyboard: no key = mid-stick, W = climb, S = descend. A unipolar `max(0, forward)` would
throw away half the travel and make mid-throttle unholdable.

### Sanitising rules, each of which is a test

| Input | Rule | Reason |
| --- | --- | --- |
| non-finite `wishX`/`wishZ` | treated as `0` **before** the bipolar remap | so throttle rests at mid-stick. Feeding `NaN` through to `ControlInput.clamped` would collapse it to `0` — motors off — which is the worst possible response to one bad packet. |
| out-of-range wish components | divided by `wishFullScale`, then clamped by `ControlInput.clamped` | clamping saturates the axis; it cannot throw. |
| non-finite or absent `lookYaw`/`lookPitch` | zero deflection on that axis, `LookTrack` **kept** | absent means "look unchanged", which really is zero deflection. Keeping the track means the next real sample measures from the last known angle rather than flicking. |
| non-finite or absent `wishFrameYaw` | fall back to the tracked yaw, then to `0` | covers a packet with `wishMovement` but no `lookOrientation`, and the future case where `movementForceRotationType = Custom` pins the frame to a fixed rotation (then the frame yaw is a constant `0`, not the head yaw). |
| first sample after launch (`LookTrack` unset) | zero pitch/roll, track initialised | otherwise arming the drone would fire a full-deflection flick from an angle nobody chose. |
| `dt` ≤ 0 or non-finite | **throws** | `dt` comes from our own tick loop, not the client. Wrong `dt` is a bug in our code, and the repo's rule is that those throw. |
| Δyaw magnitude > π | wrapped into `(−π, π]` | the pilot took the short way round. |

### Deliberately not done

- **No deadband or expo.** Keyboard sends exact zero, and stick-centre drift is a calibration
  concern (decision 11), which is blocked on real hardware. Expo belongs to #15's `RateCurve`, which
  already owns the stick-shaping job; putting a second curve here would give two places to tune the
  same feel.
- **`wishMovement.y` is ignored.** Vertical intent in Hytale's character controller rides the
  `jumping`/`crouching` booleans in `MovementStates`, not the wish vector, and throttle is already
  spoken for by the forward axis. Whether the client ever puts anything in `y` is unverified.
- **No `FpvConfig` entry.** `FpvConfig`'s own javadoc reserves it for the two decision-3 knobs and
  says per-pilot tuning belongs in `PilotProfile`. Sensitivities are per-pilot, so
  `PilotInputMapping.DEFAULT` carries them until `PilotProfile` exists.
- **No ECS system, no packet interception, no camera settings.** Wiring is #18/#24. This ticket ends
  at "a `ClientMovement` in hand becomes a `ControlInput`".

## Test strategy

`:fpv-core` carries the weight, per decision 10 — the whole reason the arithmetic is there.
`PilotInputMapperTest` with `@Nested` groups: `ThrottleFromForwardAxis`, `YawFromLateralAxis`,
`FrameRotation` (the "same stick input at four different headings yields the same sticks" test, which
is the un-rotation's real acceptance criterion), `PitchAndRollFromLookDelta` (including
tick-rate independence: half the `dt` with half the delta gives the same deflection),
`YawWrapping`, `Sanitising`, `LookTracking`. Plus value tests for `PilotInputSample`,
`LookTrack`, `PilotInputMapping` and `PilotInputUpdate`.

`:fpv-plugin` gets one small test, `ClientMovementAdapterTest`, using #34's test source set.
It needs **no** `HytaleEcsHarness`: `new ClientMovement()`, `new Position(…)` and
`new Direction(…)` are plain public-field objects with no static initialisers and no server, so the
field-copy and null-handling behaviour is directly testable. It exists to pin exactly what the shell
is allowed to be: field copies, nulls to `NaN`, and no arithmetic.

## Risks

- **The wish magnitude is a guess.** If full deflection is not `1.0`, throttle and yaw will be
  wrong by a scale factor. Contained to one config value, and the failure mode is legible while
  flying ("throttle is either off or full", or "yaw barely responds"), which is what #24 is for.
- **The look full-scale rate is a guess.** Same shape: too low and the sticks saturate on any
  movement, too high and the drone feels dead. Same fix.
- **`wishMovement` reaching us at all depends on the queue-timing problem above.** Not this
  ticket's code, but it can block #24 and the ticket that hits it should not have to rediscover it.
- **Delta on pitch cannot be held.** The mitigation is an argument about how acro flying works, not
  a measurement. If #24 says otherwise, packet 111's `relativeMotion` is the documented plan B.
